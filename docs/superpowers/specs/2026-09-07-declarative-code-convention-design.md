# 선언적 코드·설명·YAGNI 컨벤션 설계

## 문제

현재 공통 컨벤션은 복잡한 조건과 comprehension을 분리하라고 안내하지만, 어떤 표현을 추출해야 하는지와 JSX·조건문·함수 인자에서 긴 표현식을 어떻게 다뤄야 하는지가 충분히 구체적이지 않다. 또한 Python·TypeScript 집계 규칙의 G10은 변수를 사용 위치 가까이에 선언하라고 하므로, 의도를 설명하기 위해 추출한 변수의 위치를 사용처와 가깝게 두어야 한다고 오해할 수 있다.

코드 리뷰에는 현재 필요한 범위를 넘어선 예외 처리, 미래 확장용 추상화와 사용하지 않는 필드를 걸러내는 YAGNI 기준이 명시되어 있지 않다. 복잡한 설명을 요청받았을 때의 설명 수준도 일반적인 도메인 용어 우선 규칙과 구분되어 있지 않다. Python 코드 생성에서는 요구사항에 없는 오류 코드와 방대한 오류 처리 구조가 추가될 여지가 있다.

## 목적

코드의 구현을 다시 해석하지 않아도 이름만으로 의도를 파악할 수 있도록 선언적 코드 작성 기준을 명확히 한다. 추출 여부는 표현식의 길이나 변수와 사용처 사이의 거리가 아니라 의도 전달의 필요성으로 판단하게 한다.

현재 지원해야 하는 시나리오와 현실적인 실패 가능성에 집중해 과설계를 줄이고, 사용자가 복잡한 설명을 요청하면 이해 가능한 수준으로 설명한다. Python 코드에서는 요구사항과 기존 계약에 근거한 오류 처리만 생성하게 한다.

## 현재 구조와 제약

- 모든 파일에 적용되는 공통 규칙은 `conventions/general.md`에서 관리한다.
- `.py`와 TypeScript·JavaScript 파일에는 각각 `conventions/python/python-clean-code.md`와 `conventions/typescript/typescript-clean-code.md`가 추가로 적용된다.
- 두 언어별 집계 규칙에는 G10이 있으며, 일반 변수는 사용 위치 가까이에 선언하도록 안내한다.
- 같은 규칙을 언어별 파일에 반복해서 추가하면 규칙이 분기되고 서로 달라질 수 있다.
- 기존의 F3(플래그 인수 금지), G23(다형성 우선), G34(추상화 수준 일관성)과 의미가 충돌하지 않아야 한다.
- 기존의 PR·코드 전달 규칙과 사용자 요청 시 설명 수준의 예외가 충돌하지 않아야 한다.

## 결정

### 공통 규칙을 확장한다

`conventions/general.md`의 `조건과 반복 로직의 의도 표현` 항목을 `선언적 코드와 의도 표현`으로 확장한다. 다음 기준을 한 곳에서 관리한다.

- 코드만 읽어서는 의도를 파악하기 어려운 표현은 의미 있는 변수나 함수로 추출한다.
- 여러 조건이나 도메인 판단이 결합된 표현은 Boolean 판단 변수나 판단 함수로 추출한다.
- 의미 있는 연산은 이름 있는 함수나 변수로 표현한다.
- JSX, `if`, 함수 인자에 긴 표현식을 직접 넣지 않는다.
- 단순한 표현식이나 일회성 별칭까지 과도하게 추출하지 않는다.
- 추출한 변수의 위치는 사용처와의 거리보다 코드 흐름과 개념적 응집성을 기준으로 정한다.

React와 Python 예시는 이 공통 항목의 대표 예시로만 둔다. 별도 convention pack이나 언어별 중복 규칙은 만들지 않는다.

### 기존 G10을 예외와 함께 명확히 한다

Python·TypeScript 집계 규칙의 G10을 다음 의미로 수정한다.

> 일반 변수는 사용 위치 가까이에 선언한다. 단, 의도를 설명하기 위해 추출한 변수는 코드 흐름과 개념 단위가 더 잘 드러나는 위치에 둘 수 있다.

이렇게 하면 일반적인 지역성 원칙은 유지하면서 선언적 코드 작성 규칙과의 충돌을 제거한다.

### 과잉 추출을 제한한다

Boolean 변수 추출은 함수의 Boolean 플래그 인자를 허용하는 의미가 아니다. 타입별 분기가 커지는 경우에는 긴 조건을 Boolean으로 숨기지 않고 다형성이나 전략 객체를 검토한다.

### YAGNI 기준을 공통 리뷰 규칙으로 추가한다

공통 컨벤션에 과설계 코드 리뷰 기준을 추가한다.

- 현재 지원해야 하는 시나리오인지 확인한다.
- 실패 가능성이 현실적인지 확인한다.
- 단순 방어 코드인지 실제 요구사항인지 구분한다.
- 발생 확률이 매우 낮은 예외 케이스, 미래 확장용 추상화, 사용하지 않는 옵션·분기·DTO 필드, production에 불필요한 호환·중복 검증 코드는 제거 후보로 둔다.

### 복잡한 설명의 수준을 명시한다

기존의 “장황한 설명이나 자체 비유 대신 정확한 도메인 용어를 사용한다”는 규칙은 일반적인 코드·PR 전달에 유지한다. 사용자가 복잡한 설명을 명시적으로 요청한 경우에는 다음 예외를 적용한다.

> 왜 이렇게 되는지 12살한테 설명하듯 알려줘.

이 경우 쉬운 말, 단계적 설명과 필요한 예시를 사용한다. 이 규칙은 코드 자체나 PR 형식의 필수 내용을 변경하지 않는다.

### Python 오류 처리 생성을 제한한다

Python 팩에 다음 생성·리뷰 기준을 추가한다.

- 요구사항이나 기존 계약에 근거한 오류만 구현한다.
- 임의의 오류 코드, 커스텀 예외, 범용 `try/except`, 추가 validator와 호환성 처리 코드를 만들지 않는다.
- 예상치 못한 오류를 조용히 삼키거나 근거 없이 다른 오류로 변환하지 않는다.
- 실제로 지원해야 하는 입력 경계와 실패 경로의 검증은 생략하지 않는다.

## 비목표

- 모든 표현식을 변수나 함수로 추출하도록 강제하지 않는다.
- 별도 `declarative` convention pack을 추가하지 않는다.
- React·Python·TypeScript 파일에 동일한 설명을 반복해서 추가하지 않는다.
- 기존 코드의 대규모 리팩터링이나 이름 변경을 수행하지 않는다.
- 복잡한 설명 요청이 없는 상황에서 모든 응답을 어린이 대상 문체로 바꾸지 않는다.
- 요구사항에 근거한 입력 검증과 오류 처리를 제거하지 않는다.

## 완료 기준

- `conventions/general.md`에 선언적 코드 작성 기준과 React·Python 예시가 있다.
- Python·TypeScript의 G10이 의도 설명용 추출 변수 예외를 명시한다.
- `conventions/general.md`에 YAGNI 기반 과설계 리뷰 기준과 복잡한 설명 요청 예외가 있다.
- Python 팩에 근거 없는 오류 코드·예외 구조·범용 방어 코드 생성을 제한하는 기준이 있다.
- 기존 조건·반복 로직 규칙과 중복되거나 모순되는 문장이 남지 않는다.
- 계약 테스트와 plugin validator가 통과한다.
- 문서 변경으로 인해 기존 convention registry 구조가 바뀌지 않는다.
