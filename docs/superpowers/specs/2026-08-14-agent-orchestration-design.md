# 에이전트 오케스트레이션 플러그인 설계

## 문제 배경

AI 코딩 에이전트가 만든 결과는 구현 속도는 높이지만, 다음 문제가 남는다.

- 작업 규모와 무관하게 같은 절차를 적용하면 작은 변경은 무거워지고 큰 변경은 검토 지점이 부족해진다.
- brainstorming이 사용자의 결정을 대신한 뒤 spec을 완성하면, 사용자는 이미 굳어진 결과를 사후 리뷰하게 된다.
- superpowers 문서가 작업 로그와 시행착오 위주로 남으면 PR 작성에 필요한 문제 배경, 제약, 설계 근거가 사라진다.
- 통과하는 테스트가 실제 결함을 잡는지는 별도로 검증되지 않는다.
- AI가 만든 변경을 사용자가 실제로 설명하고 진단할 수 있는지는 코드 리뷰만으로 확인하기 어렵다.
- 언어와 프레임워크가 늘어날수록 컨벤션이 하나의 거대한 프롬프트로 섞일 위험이 있다.
- AI가 쓴 spec, plan, PR이 사용자의 말투와 표현법이 아니면 내용이 맞아도 잘 읽히지 않아 검토가 느려진다. 문체 지침을 플러그인 안에 문자열로 박아 두면 그 문체는 사용자가 정한 적이 없는 문체가 된다.

## 목적

Codex와 Claude Code에서 함께 사용할 수 있는 agent orchestration 플러그인을 만든다. 플러그인은 작업 규모에 맞는 흐름을 선택하고, 사용자 결정이 spec보다 먼저 일어나게 하며, TDD 이후 테스트 민감도를 검증한다. 사용자는 필요할 때 TDD 기반 구현, 테스트 민감도 검증, 작업 이해 세션과 PR 작성을 각각 독립적으로 호출할 수 있다.

## 비목표

- 모든 언어와 테스트 프레임워크를 지원하는 자동 mutation testing 엔진을 처음부터 만들지 않는다.
- 작업 이해 세션을 필수 게이트나 점수형 시험으로 운영하지 않는다.
- 작업 로그, 원시 테스트 출력, 시행착오를 장기 지식 문서로 보존하지 않는다.
- 기존 superpowers를 포크하거나 동일 기능을 다시 구현하지 않는다.
- 모든 코딩 컨벤션을 초기 버전에 완성하지 않는다.
- TDD, 테스트 민감도, 작업 이해 등 모든 skill에 command를 만들지 않는다. 초기 command 범위는 Git 작업으로 제한한다.

## 현재 구조와 제약

- 저장소에는 `CODE_CONVENTION.md`, `CLEAN_CODE.md`, `REACT_CONVENTION.md`가 초안으로 존재한다.
- 기준 워크플로우는 `work-scale-workflow`의 소형/중형/대형 분류와 superpowers 체인을 재사용한다.
- 질문 설계는 Adept의 `question-design.md`를 기준으로 한다.
- Codex와 Claude Code는 같은 Agent Skills 형식의 `skills/<name>/SKILL.md`를 사용할 수 있다.
- 플러그인 manifest는 `.codex-plugin/plugin.json`과 `.claude-plugin/plugin.json`으로 분리한다.
- Claude 플러그인 agent는 `agents/*.md`, Codex custom agent는 `.codex/agents/*.toml`을 사용하므로 agent 정의는 플랫폼 어댑터가 필요하다.
- Codex 플러그인이 프로젝트 범위 custom agent 설치를 직접 표준화하지 않으므로, Codex agent 설정은 설치 스크립트 또는 setup skill로 대상 저장소의 `.codex/agents/`에 명시적으로 설치한다.
- `CONTEXT.md`는 구현 결정이 아닌 용어집으로만 유지한다.

## 언어 정책

- 사용자에게 보이는 질문, 선택지, 설명, spec, plan, PR 본문, 이해 질문은 한국어로 작성한다.
- `SKILL.md` 본문과 agent 지침도 한국어를 기본으로 하여 두 호스트가 같은 표현과 산출물 계약을 따른다.
- 파일명, skill/agent 이름, 코드 식별자, 명령어, JSON/TOML 키처럼 플랫폼 또는 도구가 해석하는 요소는 영어를 유지한다.
- 외부 프로젝트가 별도 출력 언어를 명시하면 해당 프로젝트 규칙이 이 기본값보다 우선한다.
- 언어는 한국어로 고정하되 문체는 고정하지 않는다. 사용자 문체 프로파일이 있으면 문체 층위에서 이 문서의 기본 문체 지침보다 우선한다.

## 전체 워크플로우

```text
작업 규모 판정
  -> 범위 탐색 및 의사결정 목록화(brainstorming)
  -> 의사결정 우선 그릴(모든 실질적 spec 결정 사용자 확정)
  -> spec 작성
  -> 사용자 spec 리뷰
  -> plan 작성 + 기술 합의 질문(필요한 결정을 하나씩 사용자 확정)
  -> plan 완성(사용자 plan 리뷰 없음)
  -> TDD 기반 구현(`implement-with-tdd`)
  -> 일반 검증
  -> 테스트 민감도 검증
  -> [선택] 사용자가 작업 이해 세션 호출
  -> PR 작성 호출(`write-pr`)
  -> 해당 에이전트가 spec + 실제 diff + 최종 검증 근거 확인
  -> 해당 에이전트가 PR 초안 작성
  -> 사용자 승인 후 PR 생성
```

## 규모별 적용


| 규모  | 판정 기준                 | 의사결정 우선 그릴              | 계획/실행                               |
| --- | --------------------- | ----------------------- | ----------------------------------- |
| 소형  | 버그 또는 한두 파일 변경, PR 1개 | 기본 생략. 모호할 때만 1~2문항 단축형 | 필요 최소 절차, 현재 작업공간 우선                |
| 중형  | 하나의 기능이 PR 1개로 완결     | 필수                      | spec 승인 후 기술 합의 질문과 plan 완성, 이후 TDD |
| 대형  | 여러 독립 모듈 또는 PR 필요     | 필수, 모듈 간 계약 포함          | 전체 spec 1개, 독립 산출물별 plan/PR 분리      |


규모는 예상 시간보다 독립적으로 병합하고 검증할 수 있는 산출물 경계로 판정한다.

## 주요 설계 결정

### 1. 의사결정은 spec 작성 전에 확정한다

중형과 대형 작업은 brainstorming으로 범위를 탐색하면서 spec 작성에 필요한 실질적 의사결정을 먼저 전수 목록화한 뒤 의사결정 우선 그릴을 반드시 수행한다. 대상은 대화에서 이미 미결정으로 드러난 항목에 한정하지 않는다. 에이전트가 관례나 추천안으로 대신 정할 수 있는 항목도 spec의 범위, 행위, 계약 또는 완료 기준에 영향을 준다면 사용자에게 물어야 한다.

각 의사결정에는 2~3개 선택지, 트레이드오프, 추천안을 제시하고 한 번에 한 질문씩 사용자에게 묻는다. 선택과 이유를 기록하고, 목록화한 모든 실질적 결정이 확정됐음을 사용자와 확인한 후에만 spec을 작성한다. spec 작성 중 새로운 실질적 결정이 발견되면 임의로 채우지 않고 그릴로 돌아간다.

실질적 의사결정에는 다음이 포함된다.

- 목표, 범위, 비목표 또는 사용자에게 보이는 행위
- 시스템 경계, 공개 인터페이스, 데이터 소유권과 계약
- 보안, 운영, 호환성, migration과 되돌리기 정책
- 테스트 전략과 완료 기준
- 독립 산출물, PR 분할, 호스트별 책임

쉽게 되돌릴 수 있고 외부 계약이나 결과에 영향을 주지 않는 파일명, 내부 함수명, 사소한 구현 순서 등은 plan에서 agent가 정하며 사용자 질문 대상에서 제외한다.

이유: 사용자가 완성된 문서를 사후 승인하는 대신, 문서를 결정한 사람으로 참여해야 이후 spec 리뷰와 구현 결과 리뷰가 쉬워진다.

### 2. 결정 기록은 spec과 PR에 둔다

- `CONTEXT.md`: 합의된 도메인 용어만 기록한다.
- spec: 문제 배경, 목적, 현재 구조와 제약, 검토한 대안, 선택과 이유를 기록한다.
- plan: 확정된 결정을 반복 설명하지 않고 구현 및 검증 순서를 기록한다.
- PR: 최종 구현과 직접 관련된 결정, 이유, 테스트 결과를 사람이 이해할 수 있게 요약한다.
- ADR: 되돌리기 어렵고, 맥락 없이 놀라우며, 실제 트레이드오프가 있는 결정에만 예외적으로 사용한다.

### 3. plan은 기술 합의를 거쳐 작성하되 사용자 리뷰를 요구하지 않는다

승인된 spec이 사람의 핵심 설계 검토 지점이다. plan은 agent가 구현 순서, 파일, 테스트 절차를 구체화하는 실행 문서이며, 완성된 전체 내용을 사용자에게 다시 승인받지 않는다.

agent는 plan을 작성하면서 spec이 의도적으로 열어 둔 구현 수준의 기술 선택 중 공동 합의가 필요한 항목을 먼저 식별한다. 각 항목에 2~3개 선택지, 트레이드오프와 추천안을 제시하고 한 번에 하나씩 사용자에게 묻는다. 선택이 확정되면 plan에 반영하고 다음 질문으로 진행한다. 대표 대상은 다음과 같다.

- 주요 라이브러리, 프레임워크 기능 또는 외부 의존성 선택
- 내부 모듈 분리, 저장 방식, 오류 처리, 동시성 또는 성능 전략
- 배포 순서, feature flag, 관측성 또는 운영상 복구 방식
- 구체적인 테스트 계층, fixture, mock 또는 테스트 격리 전략

파일명, 내부 함수명, 단순 구현 순서처럼 공동 합의가 필요하지 않은 세부사항은 agent가 정한다. plan 작성 중 목표, 범위, 사용자에게 보이는 행위, 공개 계약 또는 완료 기준을 바꿔야 하는 문제가 발견되면 계획 기술 합의로 처리하지 않고 spec 수정과 사용자 리뷰 단계로 돌아간다.

모든 기술 합의가 plan에 반영되면 agent가 plan을 완성하고 TDD 구현으로 진행한다. 사용자는 원할 때 plan을 열람할 수 있지만 기본 blocking gate는 아니다.

### 4. 명시적 실행 기능은 독립 skill로 분리하고 Git 작업만 command를 제공한다

사용자가 특정 단계만 직접 실행할 수 있도록 `implement-with-tdd`, `verify-test-sensitivity`, `understand-work`, `commit-changes`, `write-issue`, `post-git-comment`, `write-pr`를 안정된 이름과 단일 책임을 가진 독립 skill로 둔다. `orchestrate-work`는 개발 흐름에 필요한 진입점만 순서에 맞게 조합할 뿐 각 기능의 세부 절차를 소유하거나 복제하지 않는다.

Codex와 Claude Code용 command는 command 하나가 skill 하나에 1:1로 위임하는 얇은 adapter로 만든다. command는 인자 전달과 해당 skill 호출만 담당하며 판단, provider 감지, 상태 전이, 검증 또는 문서 생성 로직을 포함하지 않는다. 여러 기능을 mode 인자로 분기하는 단일 만능 command는 만들지 않는다.

초기 command는 `git-commit`, `git-issue`, `git-comment`, `git-pr` 네 개다. 각각 `commit-changes`, `write-issue`, `post-git-comment`, `write-pr`에 위임한다. issue, comment와 PR은 `origin` remote를 기준으로 GitHub와 GitLab을 자동 감지하고 해당 provider의 `gh` 또는 `glab`을 사용한다. 감지 결과가 모호하거나 필요한 CLI가 없으면 외부 쓰기를 시도하지 않는다. commit 실행과 외부 issue, comment, PR 생성 및 필요한 push는 사용자에게 초안과 실행 범위를 보여주고 승인받은 뒤에만 수행한다.

### 5. 작업 이해 세션은 사용자 수동 호출형이다

작업 이해 세션은 조직용 산출물 관리나 PR blocking gate가 아니다. 사용자가 변경에 대한 자신의 이해를 확인하고 넓히고 싶을 때 Codex, Claude Code 또는 다른 호환 코딩 에이전트에서 `understand-work` skill을 명시적으로 호출한다. 향후 slash command가 추가되더라도 이 skill에만 위임한다. 호출하지 않아도 구현, PR 작성 또는 PR 생성은 차단되지 않는다.

세션은 승인된 spec, 현재 실제 diff, 연결된 이슈와 ADR, 변경과 직접 관련된 기존 문서를 근거로 사용한다. 별도 산출물 등록부, 정답지 또는 이해 기록 파일을 만들지 않고 질문과 피드백은 현재 대화에만 남긴다.

### 6. 이해 질문은 다섯 이해 축에서 최대 5개를 선정한다

에이전트는 먼저 실제 근거에서 잘못 이해하면 유지보수 판단을 그르칠 핵심 주장, 결정, 불변식, 경계와 실패 지점을 전수 목록화한다. 그다음 위험도와 유지보수 중요도를 기준으로 다음 이해 축에서 적용 가능한 질문을 최대 5개 선정한다.

1. 사양 설명: 해결하는 문제, 기대 동작과 비목표를 자신의 말로 설명할 수 있는가?
2. 구조와 실행 흐름: 요청, 데이터 또는 상태가 어떤 구성요소를 거쳐 처리되는지 설명할 수 있는가?
3. 핵심 결정과 제약: 선택 이유와 변경할 때 지켜야 할 경계를 아는가?
4. 문제 진단과 변경 위치: 증상이 발생했을 때 어느 파일, 모듈 또는 계약부터 확인하고 수정할지 아는가?
5. 검증과 영향 범위: 어떤 테스트가 행위를 보장하고 수정 시 어디까지 영향을 확인해야 하는지 아는가?

질문 하나에는 판단 하나만 둔다. 모든 변경에 다섯 축을 억지로 적용하지 않으며 실제 근거가 있는 축만 사용한다.

### 7. 이해 세션은 질문을 하나씩 진행하고 모든 선정 문항을 완료한다

Adept의 상황 우선, 실제 업무와 같은 응답 형태, 회상 질문 금지, 대부분 성공 가능한 난이도 원칙을 적용한다. 다만 핵심 주장마다 문항을 하나씩 만드는 규칙은 사용하지 않고, 전수 목록화한 주장 중 최대 5개만 우선순위화한다.

선정된 질문은 한 번에 하나씩 묻는다. 각 답변 후 사용자가 이해한 부분, 빠뜨리거나 혼동한 부분, 이를 보완하는 설명과 근거 위치를 제공한다. 아직 묻지 않은 질문은 이전 답변에 맞게 조정할 수 있지만 총 문항 수를 늘리지 않는다. 에이전트가 충분하다고 자율적으로 조기 종료하지 않고 선정한 문항을 모두 진행한 뒤, 마지막에 이해한 영역과 보완할 영역을 대화로 요약한다.

### 8. 테스트 민감도 검증은 변경 영향 범위에 적용한다

대상은 새로 작성한 테스트와 변경한 동작의 영향 범위에 있는 기존 테스트다. 전체 테스트 스위트를 무조건 mutation 대상으로 삼지 않는다.

절차는 다음과 같다.

1. TDD로 테스트와 구현을 완료하고 일반 검증을 통과시킨다.
2. 검증하려는 핵심 행위와 이를 잡아야 하는 테스트를 연결한다.
3. 해당 행위를 깨뜨리는 작은 결함 하나를 임시로 주입한다.
4. 관련 테스트를 실행한다.
5. 실패하면 테스트가 결함에 민감하다는 좋은 신호로 기록한다.
6. 통과하면 테스트 공백으로 처리하고 테스트를 보강한 뒤 다시 검증한다.
7. 임시 결함을 정확히 제거하고 원본 구현의 전체 관련 테스트를 다시 실행한다.

초기 버전은 언어/프레임워크별 mutation recipe를 제공한다. 자동 mutation runner는 범위에서 제외한다. 초기 recipe는 공통, TypeScript/JavaScript, Python, Java를 포함하고 boolean 반전, 경계값 변경, 예외 제거, 필터 조건 완화, 상태 전이 생략을 다룬다.

### 9. PR 작성 컨텍스트는 별도 산출물이 아니다

결정 배경과 설계 근거의 원본은 승인된 superpowers spec이다. PR 작성을 호출받은 코딩 에이전트는 별도의 중간 문서를 만들지 않고 다음 근거를 직접 읽어 PR을 작성한다.

- 승인된 spec: 문제 배경, 목적, 비목표, 현재 구조와 제약, 대안, 결정과 이유
- 실제 diff: 최종 구현 범위와 리뷰 포인트
- 최종 검증 근거: TDD 결과, 테스트 명령과 결과, 테스트 민감도 검증 결과
- 남은 위험과 후속 작업

이 근거 묶음을 `PR 작성 컨텍스트`라고 부르지만 별도 파일로 저장하지 않는다. spec과 plan에는 단순 작업 로그나 시행착오를 남기지 않으며, PR 본문은 위 근거에서 최종 상태만 설명한다.

### 10. PR 작성 에이전트는 사용자가 호출 시점에 선택한다

워크플로우는 특정 에이전트에게 PR 작성 책임을 고정하거나 다른 세션을 자동으로 열지 않는다. 사용자는 구현이 끝난 뒤 원하는 Codex, Claude Code 또는 다른 호환 코딩 에이전트 세션에서 `write-pr` skill 또는 `git-pr` command를 명시적으로 호출한다. `git-pr`은 이 skill에만 위임한다.

호출받은 에이전트는 다음 순서로 작업한다.

1. 승인된 spec을 읽어 문제 배경, 목적, 비목표, 결정과 이유를 확인한다.
2. 현재 저장소의 실제 diff를 직접 읽어 최종 변경 범위와 리뷰 포인트를 확인한다.
3. 실행한 명령과 결과가 있는 최종 검증 근거를 확인하고, 근거가 없거나 현재 diff와 일치하지 않으면 PR 작성을 중단한다.
4. 위 근거에서 한국어 PR 제목과 본문 초안을 작성해 사용자에게 보여주고, 명시적 승인 후에만 외부 PR을 생성한다.

구현 에이전트와 PR 작성 에이전트가 달라도 별도 중간 문서는 만들지 않는다. 선택한 세션이 같은 작업공간의 원본 spec, diff, 검증 근거에 접근할 수 있어야 한다.

### 11. 컨벤션은 선택 가능한 팩으로 확장한다

공통 clean code, coding boundary, React를 초기 팩으로 옮기고 Python, Java 등을 이후 추가한다. 라우터는 저장소의 실제 언어/프레임워크와 변경 파일을 근거로 필요한 팩만 선택한다. 프로젝트 자체 규칙이 플러그인 기본 팩보다 우선한다.

### 12. 문체는 사용자에게서 1회 수집해 전역 프로파일로 보관한다

문체 지침을 skill과 agent 안에 문자열로 박지 않는다. 대신 `capture-authoring-voice`가 인터뷰로 사용자 문체를 수집해 `voice-profile.md` 하나를 만들고, spec, plan, PR 본문, 사용자 대면 질문과 선택지 문구는 이 파일을 읽어 문체를 결정한다.

- **수집 방법**: 인터뷰 질문형. 기존 산출물을 수집해 분석하지 않는다.
- **깊이**: 고정 축을 전수 질문하며 한 번에 하나씩 묻는다. 미응답 축은 `미정`으로 남기고 그 축에 대해서는 어떤 문체 지시도 만들지 않는다. 추정으로 채우면 프로파일이 노이즈가 된다.
- **범위**: 전역 1개. 문체는 저장소가 아니라 사람에게 붙는다. 경로는 호스트 중립으로 `$AGENT_ORCHESTRATION_HOME/voice-profile.md`이며, 미설정 시 `~/.agent-orchestration/voice-profile.md`를 쓴다.
- **검증**: 저장 전에 초안 프로파일로 짧은 PR 본문을 한 편 생성해 사용자에게 보여주고, 어긋난 축만 재질문한 뒤 다시 생성한다. 사용자가 승인해야 저장한다.
- **부재 시**: 게이트를 만들지 않는다. 1회 안내 후 기본 문체로 진행한다.

고정 축은 문장 길이와 호흡, 어미와 경어체, PR 최상단 내용과 섹션 순서, 비유 허용 범위, 기술용어 원어 유지 정도, 불확실성 표현법, 금지 표현, 강조 수단, 코드와 명령 인용 밀도, 독자 가정이다.

**우선순위와 그 경계**: 문체가 충돌하면 프로파일이 플러그인 기본값을 이긴다. 다만 프로파일이 지배하는 것은 문체뿐이다. "명령 근거 없이 테스트 결과를 주장하지 않는다", "결정과 구현 세부를 구분한다", 템플릿의 고정 절 구조 같은 항목은 문체가 아니라 내용 계약이므로 프로파일 대상이 아니며 그대로 유지된다.

이유: 사용자가 읽지 않는 문서는 검토 게이트로 작동하지 않는다. 문체는 품질 기준이 아니라 취향이므로 기본값의 출처를 설계자가 아니라 사용자로 옮긴다.

| plan         | 합의된 기술 선택, 실행 및 검증 순서 | 작업 중 기준, 정책에 따라 PR 전 제거 가능       |

## 오류 및 중단 정책

- spec 사용자 승인이 없으면 plan으로 진행하지 않는다. plan 작성 중 필요한 기술 합의가 미확정이면 구현으로 진행하지 않는다. spec 수준의 변경이 필요하면 spec 수정과 사용자 리뷰로 돌아간다.
- mutation 후 관련 테스트가 통과하면 성공으로 간주하지 않는다. 테스트 보강 전까지 gate는 실패다.
- 임시 결함이 복원되지 않았거나 원본 상태의 재검증이 없으면 완료로 간주하지 않는다.
- 승인된 spec, 실제 diff 또는 현재 변경에 대응하는 최종 검증 근거를 확인할 수 없으면 PR 작성을 중단하고 부족한 근거를 보고한다.
- 외부 PR 생성은 사용자 초안 승인 전에는 수행하지 않는다.

## 초기 완료 기준

- 동일한 `skills/`가 Codex와 Claude Code 양쪽에서 로드된다.
- 두 manifest가 각 플랫폼 검증을 통과한다.
- 소형, 중형, 대형 예시가 올바른 워크플로우로 라우팅된다.
- 중형/대형 예시에서 decision-first grill 없이 spec이 생성되지 않는다.
- plan 작성 중 공동 합의가 필요한 기술 선택은 하나씩 질문하고 기록하며, 완성된 plan 전체에 대한 사용자 리뷰는 요구하지 않는다.
- `implement-with-tdd`, `verify-test-sensitivity`, `understand-work`, `write-pr`가 서로 다른 독립 skill 진입점으로 제공되고 `orchestrate-work`가 이를 조합한다.
- Git command 네 개가 대응 skill 하나에만 1:1로 위임하며 provider 감지와 업무 로직은 skill이 담당한다.
- TDD 이후 테스트 민감도 검증이 실패/통과 신호를 올바르게 판정하고 mutation 복원을 요구한다.
- 사용자가 `understand-work`를 호출하면 실제 작업 근거에서 다섯 이해 축의 질문이 최대 5개 생성되고, 질문별 피드백과 최종 이해 요약이 대화에만 남는다.
- 사용자가 선택한 코딩 에이전트에서 PR 작성을 명시적으로 호출할 수 있다.
- 호출받은 에이전트는 승인된 spec, 실제 diff와 최종 검증 근거를 직접 확인해 문제 배경, 결정, 검증 결과가 포함된 PR 초안을 작성한다.
- 구현 에이전트와 PR 작성 에이전트가 달라도 별도 중간 문서를 생성하지 않는다.
- 컨벤션 팩은 변경 기술에 맞게 선택되고 프로젝트 규칙보다 우선하지 않는다.
- 사용자 대면 산출물과 상호작용은 별도 프로젝트 규칙이 없는 한 한국어로 생성된다.
- 문체 인터뷰가 고정 축을 전수 질문하고, 미응답 축을 추정으로 채우지 않으며, 저장 전 샘플 PR로 사용자 확인을 받는다.
- 문체 프로파일이 있으면 spec, plan, PR 본문, 사용자 대면 질문 문구가 플러그인에 박힌 기본 문체 대신 프로파일을 따르고, 프로파일이 없으면 차단하지 않고 기본값으로 진행한다.
