# 과하게 통제적인 하네스 덜어내기

- 상태: 기준본
- 관련 이슈: https://github.com/Yeonny0723/agent-orchestration/issues/5
- 작업 브랜치: `refactor/5-simplify-orchestration-harness`

## 배경

한번에 전체 사양을 검토하고 승인한 뒤 정해진 절차를 따라가는 방식보다, 작은 단위로 이해하고 실행한 결과를 살펴 접근법을 바꾸는 반복 과정이 실제 개발에 더 잘 맞는다.

현재 하네스는 작업 규모 판정, 의사결정 전수 확정, spec 승인, 계획 기술 합의, TDD, 테스트 민감도 검증을 고정된 순서로 연결한다. 이 구조는 안전장치를 제공하지만 LLM 코딩 에이전트가 작업 맥락에 따라 판단할 수 있는 Task 경계, 질문 시점, 참고 자료, 테스트 전략과 검증 깊이까지 통제한다. 여러 skill 사이의 위임과 중복 승인도 흐름을 복잡하게 만든다.

간소화는 초기 spec 검토의 깊이를 줄이는 작업이 아니다. 초기 spec은 현재 구조를 근거로 기능 목표와 사용자 입력 단계의 Use Case를 찾고, 질문과 설계 비판을 반복해 예외 흐름과 운영 위험을 구현 전에 드러내는 중요한 산출물이다.

## 목표

1. spec을 한 번 승인하고 고정하는 문서가 아니라 작업과 함께 발전하는 living document로 바꾼다.
2. 초기 spec 단계에서는 기능 목표, 사용자 입력 Use Case, 예외 흐름과 운영 위험을 충분히 검토한다.
3. 질문과 사용자 리뷰를 통해 설계의 빈칸을 찾고 사양을 점진적으로 좁힌다.
4. 초기 검토가 끝난 spec과 Task 체크리스트를 기준 커밋으로 남긴다.
5. 이후에는 사용자가 요청한 Task 단위로 구현, 코드 리뷰와 커밋을 반복한다.
6. LLM 코딩 에이전트가 판단할 수 있는 실행 세부사항은 하네스가 강제하지 않는다.

## 비목표

- 초기 spec 검토를 생략하거나 형식적인 승인 절차로 축소하지 않는다.
- 테스트, 문서화 또는 검증 자체를 제거하지 않는다.
- 모든 프로젝트에 같은 Task 크기, 질문 수, 테스트 방식과 문서 탐색 순서를 강제하지 않는다.
- 이번 변경에서 제품 기능이나 Git provider 기능을 새로 추가하지 않는다.

## 현재 구조와 문제

### 고정된 선형 흐름

`orchestrate-work`는 작업을 소형, 중형, 대형으로 나누고 현재 단계를 정확히 하나만 유지하도록 한다. 중형과 대형 작업은 모든 실질적인 spec 결정을 확정한 뒤에만 spec을 작성할 수 있다. 이 제약은 초안을 먼저 만들고 검토하면서 사양을 좁히는 방식과 맞지 않는다.

### 중복된 판단 단계

spec 의사결정과 계획 기술 합의가 별도 단계로 나뉘지만 실제 작업에서는 구현 중 발견한 사실이 spec과 plan을 함께 바꿀 수 있다. 어느 문서에 속하는 질문인지 먼저 분류하는 비용이 생긴다.

### 검증 방식의 강제

구현은 승인된 spec과 plan을 전제로 TDD skill에 위임되고, 이후 mutation 기반 테스트 민감도 검증을 거친다. PR 작성 단계에서는 이 검증을 다시 요구한다. 위험과 변경 성격에 관계없이 같은 검증 경로를 강제한다.

### 작성 skill의 중첩

spec과 plan을 만들기 위해 brainstorming, decision-first-grill, grill-with-docs, domain-modeling과 author-reviewable-text가 연쇄적으로 개입할 수 있다. 문서를 더 잘 쓰기 위한 보조 수단이 기본 흐름을 통제한다.

### 중복 승인

사용자가 Task 결과를 코드 리뷰하고 커밋을 요청해도 `commit-changes`는 커밋 계획을 다시 제시하고 별도 승인을 요구한다. 같은 범위에 대해 승인이 반복된다.

### 구현 문구를 고정하는 테스트

현재 계약 테스트는 사용자에게 보이는 핵심 행위뿐 아니라 단계 순서, 질문 수와 특정 문구까지 검사한다. 내부 흐름을 단순화하거나 LLM의 판단 범위를 넓히기 어렵게 만든다.

## 설계 원칙

### 깊은 초기 검토

에이전트는 현재 코드와 문서를 조사한 뒤 첫 spec 초안을 작성한다. 초안이 모든 답을 포함할 필요는 없다. 확인된 사실, 가정과 미결정 사항을 구분한다.

사용자는 초안을 여러 차례 검토하며 이해되지 않는 부분과 설계 문제를 지적한다. 에이전트는 관련 질문과 구체적인 예외 상황을 사용해 빈칸을 찾고 spec을 갱신한다. 고정된 질문 수나 인터뷰 순서를 강제하지 않는다.

`decision-first-grill`은 spec 작성 전의 차단 게이트가 아니라 작성된 초안을 비판하는 전문 도구로 사용한다. 영향이 큰 빈칸, 빠진 Use Case, 예외와 운영 위험을 찾기 위해 반복해서 사용할 수 있으며 모든 결정을 확정해야 종료되는 조건은 두지 않는다.

초기 검토에서는 작업에 관련된 다음 관점을 고려한다.

- 기능 목표와 사용자 입력에서 시작하는 Use Case
- 정상 흐름과 예외 흐름
- 상태 보관과 데이터 소유권
- 시스템 사이의 입력, 출력과 공개 계약
- 크기, 비용, 성능과 자원 제한
- 오류 전달, 재시도, 복구와 부분 실패
- 로그, 추적 식별자와 운영 가시성
- 프론트엔드, 백엔드, AI 서버 등 구성요소의 책임
- 보안, 개인정보와 호환성
- 복잡도를 줄일 수 있는 대안과 MVP 제외 범위

모든 항목을 기계적인 체크리스트로 채우지 않는다. 현재 기능에 실제로 영향을 주는 관점을 에이전트가 선택하고, 빠진 중요한 관점은 사용자 리뷰에서 추가한다.

초기 기준본은 선언한 사용자 입력 경계에서 발견한 각 Use Case가 MVP 포함, 후순위 또는 제외로 정리되고, 관련 예외와 운영 위험을 검토한 뒤 사용자가 spec 전체를 기준본으로 승인하면 준비된 것으로 본다. 알 수 없는 미래의 모든 Use Case를 찾았다고 주장하지 않는다.

### 발전하는 spec

하나의 spec을 계속 갱신한다. 별도의 `draft-v2`, `final` 파일을 만들지 않으며 변경 이력은 Git으로 추적한다.

결정에는 필요한 경우 다음 상태를 표시한다.

- 검토 중: 선택지나 영향이 충분히 드러나지 않았다.
- 잠정 결정: 현재 방향은 있으나 구현 또는 추가 검토로 바뀔 수 있다.
- 확정: 현재 범위에서 구현 기준으로 사용한다.
- 후순위: 현재 구현을 막지 않으며 이후 검토한다.

MVP 제외 항목은 결정 상태와 분리해 관리한다. 구현 중 새 사실이 드러나면 확정된 결정도 이유와 영향 범위를 기록하고 수정할 수 있다.

### 간결한 Task 계획

plan은 구현을 미리 코드 수준으로 설명하지 않는다. 작업 순서와 완료 여부를 알 수 있는 체크리스트를 제공한다. 기본값은 living spec 안에 Task 체크리스트를 함께 두는 것이다. 문서가 너무 커지거나 독립적인 작업군을 분리해야 할 때는 에이전트가 별도 plan 파일로 나눌 수 있다. Task 크기, 분할, 병합과 순서는 에이전트가 현재 코드와 리뷰 부담을 보고 판단하며 사용자가 언제든 조정할 수 있다.

### Task 실행과 리뷰

사용자가 Task 시작을 요청하면 에이전트는 관련 있다고 판단한 현재 spec, plan, 코드, 문서와 변경 이력을 확인한다. 필요한 spec과 plan을 갱신하고 구현과 검증을 수행한다.

커밋 전에는 사용자에게 변경 내용, 변경 이유, 계약 영향과 검증 결과를 간략히 설명하고 코드 리뷰를 요청한다. 수정 요청이 있으면 같은 Task에서 반영한다. 사용자가 승인하면 관련 코드, 테스트, spec과 plan을 같은 커밋에 포함하고 Task를 완료 처리한다.

현재 Task가 커밋되기 전에는 다음 Task를 실행하지 않는다.

### 에이전트 자율 판단

하네스는 다음 사항을 고정하지 않는다.

- 작업 규모 등급과 Task 경계
- 확인할 문서와 Git 이력의 범위
- 질문 개수, 순서와 제시 방식
- 내부 구현 방식
- 테스트 우선 여부와 테스트 종류
- 검증 명령과 검증 깊이
- 선택형 보조 skill 사용 여부

에이전트는 판단에 필요한 정보가 없거나 사용자 선택에 따라 제품 행위, 공개 계약, 범위 또는 책임 소유권이 실질적으로 달라질 때 질문한다.

## 사용자 Use Case

### UC-1. 중요한 작업을 처음 시작한다

에이전트는 현재 구조와 관련 문서를 조사해 첫 living spec 초안을 만든다. 초안에는 기능 목표, 확인된 구조, Use Case, 예외 흐름, 결정 상태, MVP 제외 범위와 간결한 Task 체크리스트가 포함된다.

### UC-2. 사용자가 초기 spec을 반복 검토한다

사용자는 이해되지 않는 부분, 빠진 Use Case와 설계 문제를 지적한다. 에이전트는 코드 근거, 선택지, 트레이드오프와 예외 상황을 제시하고 답변에 따라 spec을 갱신한다. 이 과정을 사용자가 기준본으로 충분하다고 판단할 때까지 반복한다.

### UC-3. 초기 spec을 기준본으로 만든다

발견한 각 Use Case가 MVP 포함, 후순위 또는 제외로 정리되고 관련 예외와 운영 위험을 검토한 뒤, 사용자가 초기 spec과 Task 체크리스트를 승인하면 문서만 하나의 기준 커밋으로 남긴다. 검토 중인 후속 결정이 있어도 현재 범위와 Task 진행을 막지 않는다면 상태를 명시하고 남길 수 있다.

### UC-4. 사용자가 구현 Task를 시작한다

에이전트는 기존 결정과 이전 Task에서 달라진 계약 중 현재 Task에 관련된 내용을 자율적으로 확인한다. 필요하면 spec과 plan을 갱신한 뒤 구현과 검증을 수행한다.

### UC-5. 사용자가 Task 결과를 코드 리뷰한다

에이전트는 긴 작업 로그 대신 최종 변경과 이유, 계약 영향, 검증 결과를 간략히 설명한다. 사용자는 실제 diff를 검토하고 수정 또는 커밋을 요청한다.

### UC-6. 리뷰에서 수정이 필요하다

에이전트는 같은 Task에서 코드와 문서를 수정하고 영향을 다시 검증한다. 승인 전에는 커밋하거나 다음 Task로 진행하지 않는다.

### UC-7. 사용자가 Task 커밋을 승인한다

에이전트는 승인된 범위가 분명하면 별도의 승인 절차를 반복하지 않는다. 관련 코드, 테스트, spec과 plan만 명시적으로 stage하고 하나의 Task 커밋을 만든다.

### UC-8. 구현 결과가 기존 결정을 바꾼다

에이전트는 변경 이유와 영향을 living spec에 반영한다. 현재 Task 범위나 사용자에게 보이는 계약이 크게 달라지면 구현을 계속 밀어붙이지 않고 사용자와 방향을 다시 맞춘다.

### UC-9. 다음 Task를 요청한다

이전 Task가 커밋됐다면 다음 Task를 시작한다. 커밋되지 않았다면 이전 Task의 리뷰 또는 정리를 먼저 끝낸다.

### UC-10. 작고 명확한 작업을 요청한다

별도의 초기 spec과 plan이 가치가 없는 경우 에이전트가 생략할 수 있다. 코드 리뷰와 커밋 경계는 유지한다.

## 예외와 실패 흐름

### 관련 없는 미커밋 변경이 있다

사용자 변경을 되돌리거나 Task 커밋에 포함하지 않는다. 에이전트가 안전한 작업 방식과 커밋 범위를 판단하고, 분리할 수 없을 때만 사용자에게 알린다.

### 필요한 검증을 실행할 수 없다

실행하지 못한 검증, 이유와 남은 위험을 코드 리뷰 설명에 포함한다. 검증 부재가 완료를 막는지는 변경 위험과 저장소 규칙을 근거로 판단한다.

### Task 범위가 예상보다 커진다

에이전트는 Task를 분리하거나 plan을 조정할 수 있다. MVP 범위, 공개 계약 또는 구성요소 책임이 달라지면 사용자에게 영향을 설명한다.

### 선택형 skill이 설치되지 않았다

기본 작업을 차단하지 않는다. 설치가 결과를 실질적으로 개선하고 사용자가 원할 때만 제안한다.

### 문서와 코드가 일치하지 않는다

에이전트가 현재 코드, 문서와 이력 중 필요한 근거를 조사해 불일치를 드러낸다. 어느 자료를 우선할지는 상황에 따라 판단하며 중요한 계약 차이는 사용자와 확정한다.

## 최소 코어

### `orchestrate-work`

중요한 작업의 현재 구조를 탐색하고 living spec과 Task 체크리스트를 만드는 진입점이다. 초기 spec 리뷰를 돕지만 작업 규모 등급, 질문 수나 고정 단계 상태 머신을 강제하지 않는다.

### `execute-task`

사용자가 지정한 Task를 수행하는 진입점이다. 관련 맥락 확인, 필요한 spec·plan 갱신, 구현·검증, 코드 리뷰 설명과 승인 후 커밋까지 연결한다. 세부 구현과 검증 방법은 에이전트가 판단한다.

### `decision-first-grill`

living spec 초안을 대상으로 설계의 빈칸을 찾는 전문 도구로 유지한다. 사용자 입력 Use Case, 예외 흐름, 비용, 로그, 오류와 구성요소 책임을 비판적으로 검토하고 결과를 spec의 결정 상태에 반영한다. 중요한 작업에서는 반복해서 사용할 수 있고, 작고 명확한 작업에서는 에이전트가 생략할 수 있다.

### `implement-with-tdd`

`execute-task`를 대체하는 별도 workflow가 아니라 Task 구현 전략으로 유지한다. 사용자 요청, 저장소 규칙 또는 회귀 위험을 근거로 테스트 우선 구현이 유리할 때 사용한다. 전체 spec 확정 대신 현재 Task의 목표와 완료 조건이 구현할 만큼 분명한지를 진입 조건으로 삼는다.

### `verify-test-sensitivity`

새 테스트가 실제 결함을 감지하는지 불확실하거나 핵심 행위의 회귀 위험이 큰 경우 사용하는 전문 검증 도구로 유지한다. 모든 Task와 PR에서 의무적으로 실행하거나 이미 확보한 검증 근거를 무조건 반복하지 않는다.

### 독립 도구

컨벤션 적용, Issue·코멘트·PR 작성과 일반 커밋 같은 기능은 필요할 때 직접 호출할 수 있는 독립 도구로 유지한다. 기본 Task 흐름에 불필요하게 삽입하지 않는다.

### 선택형 도구

작업 이해 세션, 문체 수집과 domain modeling은 필요하거나 사용자가 직접 원할 때 사용할 수 있다. 외부 `grill-with-docs`, `domain-modeling`, `superpowers`, `stop-slop`과 `humanizer`가 설치되지 않아도 기본 작업을 차단하지 않는다. 설치돼 있으면 에이전트가 현재 Task에 도움이 되는 범위에서 활용할 수 있다.

## 유지할 불변식

1. 중요한 작업의 초기 spec은 현재 구조를 근거로 작성하고 사용자가 반복 검토한다.
2. 초기 spec과 Task 체크리스트는 사용자 승인 후 기준 커밋으로 남긴다.
3. Task 결과는 커밋 전에 사용자가 실제 변경을 리뷰할 수 있어야 한다.
4. Task 리뷰 승인이 없으면 커밋하지 않는다.
5. 관련 코드, 테스트, spec과 plan 변경은 같은 Task 커밋에 포함한다.
6. 현재 Task가 커밋되기 전에는 다음 Task를 실행하지 않는다.
7. unrelated 사용자 변경을 되돌리거나 커밋에 포함하지 않는다.
8. push, PR, Issue와 코멘트 게시 같은 외부 쓰기는 사용자 승인 범위를 따른다.

## MVP 제외

- 자동으로 최적 Task 크기를 계산하는 규칙 엔진
- 모든 프로젝트에 적용되는 고정 spec 질문 목록
- 자동 mutation testing 시스템
- 영구적인 사용자 이해도 점수나 학습 기록
- Task 상태를 관리하는 별도 서비스 또는 데이터베이스

## 위험과 대응

### 간소화가 사양 누락으로 이어질 수 있다

초기 spec의 반복 리뷰와 현재 구조 조사, Use Case 및 예외 흐름 검토를 핵심 불변식으로 유지한다. 질문 수와 형식 대신 사용자 리뷰 완료를 기준으로 삼는다.

### 선택형 skill이 사실상 계속 기본 흐름을 통제할 수 있다

skill description, setup 의존성, README와 acceptance 사례까지 확인해 자동 호출 경로를 제거한다.

### 호스트마다 흐름을 다르게 해석할 수 있다

내부 단계와 문구가 아니라 코드 리뷰 전 커밋 금지, 같은 Task 커밋, 다음 Task 진행 금지 같은 관찰 가능한 경계를 인수 사례로 검증한다.

### 기존 사용자의 진입점이 깨질 수 있다

기존 skill과 command 사용 현황을 확인해 유지, alias, deprecated 또는 제거 중 하나를 결정하고 문서에 반영한다.

### plugin 원본과 설치 캐시가 달라질 수 있다

원본 저장소 검증과 실제 설치·업그레이드 후 forward test를 별도 완료 조건으로 둔다.

## 완료 기준

- 중요한 작업에서 현재 구조를 조사한 living spec 초안이 먼저 생성된다.
- 초기 spec을 사용자와 반복 검토하며 기능 목표, 주요 Use Case와 예외 흐름을 좁힐 수 있다.
- 발견한 Use Case마다 MVP 포함, 후순위 또는 제외가 정해진 뒤 사용자가 초기 기준본을 승인한다.
- 미결정 사항과 MVP 제외 범위가 문서에서 구분된다.
- Task 계획은 간결한 체크리스트이며 구현 세부사항을 과도하게 고정하지 않는다.
- 사용자가 요청한 Task만 실행하고 결과를 코드 리뷰용으로 설명한다.
- 리뷰 승인 전에는 Task 커밋을 만들지 않는다.
- 승인 후 관련 코드, 테스트, spec과 plan이 같은 커밋에 포함된다.
- 현재 Task가 커밋되기 전에는 다음 Task를 실행하지 않는다.
- TDD, mutation 검증과 작성 보조 skill이 기본 workflow를 차단하지 않는다.
- 계약 테스트가 내부 문구와 고정 단계보다 사용자에게 보이는 경계를 검증한다.
- Codex와 Claude Code에서 같은 핵심 흐름을 확인할 수 있다.
