# 기능 이름

## 적용 깊이

작업 규모와 상세 설계 산출물이 필요한 이유를 적는다. 작은 변경이라면 간단한 Spec을 유지하고 다이어그램·상세 schema·Task 우선순위 표를 생략할 수 있다.

## 기능 목표

사용자가 달성하려는 결과와 성공 기준을 먼저 적는다.

## 사용자 Use Case

사용자 인터페이스에서 사용자가 시작할 수 있는 정상·대안 흐름을 폭넓게 적는다. 각 Use Case에 MVP 포함, 후순위 또는 제외를 표시하고 이유를 간단히 설명한다. 불필요하거나 가치가 낮은 흐름은 제거해 현재 범위를 좁힌다.

## 현재 구조와 제약

관련 코드와 문서, 공개 계약, 데이터 흐름, 기술·운영·호환성 제약을 적는다. 검토한 Use Case에 영향을 주는 현재 구조의 근거와 제약을 설명한다.

## 시각 설계 자료

상세 Spec 대상이면 Draw.io MCP를 사용해 아래 관련 자료를 만든다. `.drawio` 편집 원본과 PNG를 문서 폴더에 보관하고 PNG를 Markdown에 삽입한다. 각 그림은 본문 Use Case·흐름·계약과 일치시킨다. 작은 변경이나 관련 없는 그림은 생략하고 이유를 간단히 적는다.

### Use Case diagram

행위자, 시스템 경계와 주요 Use Case를 그린다. 각 Use Case의 MVP 포함·후순위·제외 처분은 `사용자 Use Case` 절과 맞춘다.

### Flow chart

주요 end-to-end 동작, 시스템 간 전달, 조건 분기와 관련 예외·복구 흐름을 그린다. 책임 경계가 중요하면 swimlane으로 나눈다.

## API 계약 및 schema

새로 만들거나 바뀌는 API별 caller/provider, method/path, 요청·응답 필드와 타입, 필수 여부·제약, 예시, 성공/실패 상태 코드·오류 형식, 인증·크기 제한·timeout·재시도 정책을 적는다. 공개 계약과 내부 API를 구분하고 필요하면 OpenAPI 또는 JSON Schema를 연결한다. 확정 여부와 미결정 경로는 결정 상태로 표시한다. API 변경이 없으면 해당 없음으로 둔다.

## DB schema 및 ERD

엔티티·필드·타입·null/default 여부·PK/FK·관계 카디널리티·unique/check 제약·인덱스·삭제/보존 정책을 적고 ERD를 연결한다. 기존 데이터 구조 재사용, migration 영향, 물리 DB를 직접 확인했는지도 밝힌다. 저장 구조가 바뀌지 않으면 해당 없음으로 둔다.

## 예외와 운영 위험

Use Case별 예외 흐름과 부분 실패, 오류 전달·복구 정책을 적는다. 해당되는 경우 기능 플래그, timeout, 재시도 횟수, 토큰·크기 한도, 비용, 성능, 로그, 보안과 개인정보를 다룬다. 프로젝트 안의 기능·데이터·운영 책임 및 비용 소유권을 구분한다.

## 결정 기록

결정과 이유, 영향을 적는다. 필요한 경우 `검토 중`, `잠정 결정`, `확정`, `후순위` 상태를 표시한다.

## MVP 제외

현재 구현에서 의도적으로 제외하는 범위를 적는다.

## 완료 기준

사용자에게 보이는 행위와 검증 가능한 완료 조건을 적는다. 목표부터 Task 계획까지 최종 리뷰가 끝나면 spec을 완료 기준본으로 표시한다.

## Task 계획
