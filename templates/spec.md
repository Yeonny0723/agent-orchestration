# 기능 이름 · Living Spec

> 문서 상태: 초안 / 검토 중 / 완료 기준본 중 현재 상태와 적용 범위를 적는다. 마지막 확인 시점과 아직 확인하지 못한 근거를 밝힌다.

이 파일은 Spec의 필수 내용과 표기 규칙의 기준이다. 작성 시 지침을 실제 내용으로 대체한다. [완성 샘플과 읽는 순서](../examples/spec/document-generation/README.md)는 적용 수준을 보여 주며, 샘플의 제품 정책·수치·API·추정치를 다른 프로젝트의 기본값으로 사용하지 않는다.

**문서 전체 원칙:** 그림에는 관계와 흐름을, 글에는 판단 기준·예외·결정 이유를 담는다. 구현 중 확인된 사실이 기존 Spec과 다르면 관련 본문·API·DB·그림·Task 및 테스트 결과를 함께 갱신한다. 현재 결론은 본문에서 바로 찾을 수 있게 하고 변경 이력은 Git으로 추적한다.

## 적용 깊이

사용자 흐름이 여러 개이거나 여러 구성요소·외부 시스템이 함께 바뀌거나 신규 공개 API·저장 데이터·도메인 관계·비동기 처리가 생기면 상세 Spec을 작성한다. 아래 절의 관련 내용과 그림을 포함한다.

계약·저장 구조·시스템 경계가 바뀌지 않는 한 모듈의 명확한 수정은 간단히 작성할 수 있다. 상세 schema, 그림, 우선순위 표 등을 생략할 때는 빠지는 검토가 없는지 확인하고 이유를 짧게 적는다. 별도 Spec 자체의 가치가 낮으면 파이프라인에서 생략을 판단할 수 있다. 관련 없는 API·DB 절은 `해당 없음`과 이유를 적는다.

## 기능 목표·범위

사용자가 얻는 결과, 성공 기준, 이번 출시에서 제공하는 기능을 짧게 적는다. 제공하지 않는 기능은 아래 `이번 출시 제외 범위`에서 명시한다.

## 사용자 Use Case

각 항목을 **“사용자가 ~할 때, ~한다”** 형식으로 쓴다. 정상 흐름뿐 아니라 재진입, 입력 변경, 진행 중 행동, 실패, 재시도, 만료를 확인한다. 허용하지 않는 행동도 화면 동작과 이유를 적는다. 해당하지 않는 경우는 이유를 남긴다.

| ID | 사용자 행동과 결과 | 출시 범위: 포함 / 후순위 / 제외 | 관련 정책·계약 |
| --- | --- | --- | --- |

행위자·시스템 경계·주요 Use Case의 관계를 보여 주는 다이어그램을 이 절에 삽입한다. 그림과 본문의 범위를 맞추고 불필요하거나 가치가 낮은 흐름은 줄인다.

## 현재 구조와 제약

관련 코드·기존 문서·공개 계약을 근거로 현재 확인된 사실과 제안·미확인 사항을 구분한다. 기술·운영·호환성 제약이 사용자 행동과 설계에 미치는 영향을 설명한다. 확인하지 않은 코드나 실제 DB 상태를 확인했다고 쓰지 않는다.

## 결정 기록

결정의 현재 상태는 다음 표기를 사용한다. 출시 제외 여부, 외부 의존성, 구현 완료 여부를 결정 성숙도와 혼동하지 않는다.

| 표기 | 의미 |
| --- | --- |
| 확정 | 현재 구현과 검증의 기준인 결론 |
| 잠정 결정 | 우선 채택했으나 명시한 조건이 확인되면 다시 판단할 결론 |
| 검토 중 | 선택이나 근거 확인이 남은 항목 |
| 후순위 | 현재 출시 범위에서 다루지 않기로 한 항목 |
| 외부 의존성 | 다른 팀·시스템의 계약이나 작업을 기다리는 조건. 결정 상태와 함께 표시 가능 |

| 항목 | 결정 상태 | 현재 결론·이유 | 바뀐 이유·영향 | 외부 의존성: 대상·담당·해제 조건 |
| --- | --- | --- | --- | --- |

결정이 바뀌면 현재 결론을 먼저 고치고 바뀐 이유와 영향받는 Use Case·API·DB·Task를 연결한다. 모든 미결정을 억지로 확정하지 않는다. 남겨 둔 항목은 현재 범위 또는 착수에 미치는 영향을 밝힌다.

## 전체 흐름·책임

Browser·각 서버·외부 시스템 사이의 요청·응답, 데이터와 바이너리 이동, 주요 분기와 실패·복구를 흐름도로 보여 준다. 역할 이름은 해당 프로젝트의 실제 구성요소에 맞춘다. 책임 경계가 중요하면 swimlane으로 나눈다.

그림 아래 글에는 상태 판정·저장·삭제의 소유자, 상태가 충돌할 때 따를 기준, 전달 데이터의 의미와 선택 이유를 적는다. 목업 경로와 최종 연계 경로가 다르면 그림의 기준과 대체 구간을 명시한다.

| 책임·데이터 | 판정 또는 생성 주체 | 저장 주체·위치 | 삭제·복구 주체와 조건 |
| --- | --- | --- | --- |

## 예외·운영 정책

Use Case별 실패 시 사용자 화면, 저장되는 이력과 최종 상태, 복구 책임을 구체적으로 적는다. timeout, 만료, 재시도, 연결 끊김, 부분 실패와 정리 실패를 검토하고 해당하지 않거나 후순위인 항목도 표시한다. 늦은 결과가 이미 확정된 상태를 덮어쓸 수 있는지도 정한다.

| 상황·조건 | 사용자에게 보이는 동작 | 저장 상태·이력 | 재시도·복구·정리와 담당 | 결정 상태 |
| --- | --- | --- | --- | --- |

관련되는 경우 시간의 기준 시점·단위·시간대, 실제 삭제 지연, 인증·권한, 크기·비용·성능·자원 한도, 로그·개인정보·호환성·기능 플래그를 적는다. 예외 정책을 결정하지 않은 경우 임의의 동작으로 채우지 않는다.

## API 계약 및 schema

새로 만들거나 바뀌는 API별로 호출 방향·담당 서버·method/path, 공개/내부 구분, 요청·응답의 필드·타입·필수 여부·제약을 적는다. 정상 요청·응답과 오류의 실제 형태를 예시로 제공한다. 인증·크기 제한·timeout·재시도 정책은 해당 정책을 연결한다. 필요하면 OpenAPI 또는 JSON Schema를 연결한다.

| 호출 방향 | 담당 서버 | method/path | 요청·응답·오류 예시 위치 | 결정 상태·외부 의존성 |
| --- | --- | --- | --- | --- |

논리 경로, context path와 프록시 경로를 구분하고 미확정 경로는 제안으로 표시한다. 목업의 임시 URL·응답을 외부 시스템의 확정 계약으로 표현하지 않는다.

## DB schema 및 ERD

기존 엔티티의 재사용·확장·신규 생성 여부와 이유를 적고 관계도를 삽입한다. 물리 DB를 확인했는지, 코드 선언 또는 제안에 근거한 것인지 밝힌다. 객체·서비스의 책임이 별도로 중요하면 Class diagram을 추가하며 ERD와 구분한다.

각 필드에 타입, null/default, PK/FK, 관련 사용자 행동과 필요한 이유를 적는다. 운영용 필드는 관련 정책을 근거로 삼는다. 관계 카디널리티·unique/check 제약·인덱스·migration 영향·삭제/보존 정책도 포함한다.

| 엔티티·필드 | 재사용 / 확장 / 신규 | 타입·제약 | 필요한 사용자 행동 또는 운영 정책 | 저장 이유 |
| --- | --- | --- | --- | --- |

## 이번 출시 제외 범위

제공하지 않는 기능과 이유, 재검토 조건을 짧게 적는다. 관련 Use Case와 결정 기록을 연결해 범위가 서로 다르게 보이지 않게 한다.

## Task 계획

설계 검토와 범위 좁히기가 끝난 뒤 작성한다. 핵심 사용자 가치를 확인하는 최소 수직 PoC 또는 주요 위험 감소를 우선하고, 선행 의존성과 후속 범위를 반영한다. PoC가 부적합하면 이유를 적는다.

우선순위, 착수 가능 여부와 완료 상태는 별도 열로 표시한다. 예상 시간에는 단위·추정 근거·검증 포함 여부를 밝히고 작업량과 외부 대기 시간을 구분한다. 근거가 부족하면 추정 보류 사유를 적는다.

- 우선순위: `P0 / P1 / P2`와 해당 출시에서의 의미를 정의한다.
- 착수 가능 여부: `지금 가능 / 목업으로 가능 / 대기`로 구분하고 해제 조건을 선행 조건에 적는다.
- 완료 상태: `미착수 / 진행 중 / 구현 완료·검증 대기 / 검증 완료`처럼 실제 근거에 맞게 표시한다. 검증 완료가 사용자 리뷰·커밋 승인까지 뜻하지는 않는다.

| ID | 담당 | 우선순위 | 작업 | 선행 조건 | 예상 시간 | 착수 가능 여부 | 완료 상태 | 완료 기준 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |

### 목업과 실제 연계

일부만 가능한 작업은 목업 작업과 실제 연계 작업으로 나누고 각각의 완료 상태를 관리한다. 대체 구간, 실제 연계 전환 조건, 검증 가능한 내용과 보장하지 못하는 내용을 적는다. 목업 검증 완료를 실제 연계 완료로 표시하지 않는다.

| 목업 Task | 실제 연계 Task | 대체 구간·전환 조건 | 목업에서 검증 가능 | 실제 연계 후 검증할 내용 |
| --- | --- | --- | --- | --- |

### 테스트 목록

Use Case·예외 정책과 Task의 완료 기준을 검증 시나리오에 연결한다. 자동·수동·목업·실제 연계 중 필요한 방법과 환경을 적는다. 실행하지 않은 검증은 완료로 표시하지 않는다.

| 검증 ID | 관련 Use Case·정책·Task | 시나리오·기대 결과 | 방법·필요 환경 | 결과·근거 |
| --- | --- | --- | --- | --- |

## 완료 기준

사용자에게 보이는 결과와 검증 가능한 완료 조건을 적는다. 문서 검토 완료와 기능 구현·검증 완료를 구분한다. 목표부터 Task 계획까지 사용자가 최종 리뷰하면 Spec을 완료 기준본으로 표시하고 남은 미결정·외부 의존성의 영향을 명시한다.

그림은 해당 절에서 바로 미리 볼 수 있도록 PNG를 상대 경로로 삽입하고 편집 가능한 `.drawio` 원본을 연결한다. 상세 Spec에는 관련 Use Case·flow·ERD를 포함한다. 그림의 기준과 본문·계약·상태 소유권이 같은지 확인한다. 파일명·내보내기·동시 갱신 방법은 [다이어그램 작성 지침](../skills/orchestrate-work/references/diagrams.md)을 따른다.
