# PR/MR 작성 규칙

## 원칙

1. **진실성 우선**: 실제 diff에 없는 변경을 쓰지 않고, 삭제·설정·의존성·CI를 포함한 유의미한 변경을 누락하지 않는다.
2. PR 본문은 코드의 지도이지 사본이 아니다. 코드 리터럴이나 기계적 변경 나열 대신 `file:line`과 심볼로 가리키고, 산문은 이유·대안·흐름·위험만 설명한다.
3. 가정, 미검증 사항과 컨벤션 추정을 숨기지 않는다.
4. 해당 없는 섹션을 채우기 위해 내용을 지어내지 않는다. 단순 변경은 Summary, Details, Verification만으로 끝날 수 있다.

## 작성 순서

1. base 대비 전체 diff, 커밋, 연결 이슈와 승인된 spec을 읽는다.
2. 변경을 파일이 아니라 의도 기준의 논리 단위로 묶는다.
3. `assets/pr-template.md`를 읽고 필요한 섹션만 채운다.
4. Self-Check로 실제 diff와 제목·본문·검증 근거가 일치하는지 확인한다.

## 섹션 규칙

- 제목은 `type(scope): 명령형 한글 요약`을 기본으로 하며 72자 이내로 쓴다.
- Summary는 이유, 핵심 변경, 영향 범위를 설명한다.
- Decisions에는 배경, 대안, 트레이드오프와 선택 이유를 남긴다.
- Verification에는 실제 실행한 명령만 기록한다.
- Review Points에는 되돌리기 어렵거나 피해가 큰 지점을 `file:line`과 이유로 표시한다.
- Risk / Rollback에는 알려진 위험과 실제 가능한 복구 방법만 쓴다.
