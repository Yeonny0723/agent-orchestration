# Task 실행

## 범위 확인

사용자가 지정한 Task만 수행한다. 현재 Task가 없다면 요청에서 리뷰 가능한 작업 단위를 정한다.

현재 spec, plan, 관련 코드·문서와 변경 이력 중 결과에 필요한 근거를 에이전트가 판단해 확인한다. 기존 계약이 바뀌었거나 구현으로 새 사실이 드러나면 같은 Task에서 spec과 plan을 갱신한다. 관련 없는 변경은 되돌리거나 커밋에 포함하지 않는다.

제품 행위, 공개 계약, 범위 또는 책임 소유권이 사용자 선택에 따라 달라지고 근거만으로 판단할 수 없을 때 질문한다.

## 구현과 검증

Task의 목표와 완료 조건에 맞게 구현한다. 구현 방식, 테스트 우선 여부, 테스트 종류와 검증 깊이는 사용자 지시, 저장소 규칙과 회귀 위험을 근거로 판단한다.

필요하면 다음 전문 도구를 선택한다.

- `apply-conventions`: 변경 파일에 적용할 프로젝트 규칙이 필요할 때
- `implement-with-tdd`: 테스트 우선 구현이 유리할 때
- `verify-test-sensitivity`: 새 테스트의 결함 감지력이 불확실하거나 회귀 위험이 클 때

도구가 설치되지 않았거나 가치가 낮으면 기본 작업을 계속한다. 실행하지 못한 검증과 남은 위험은 리뷰 설명에 포함한다.

## 사용자 리뷰

최종 diff를 자체 검토한 뒤 다음 내용을 간략히 설명한다.

- 변경 내용과 이유
- 사용자 또는 공개 계약 영향
- 실행한 검증과 결과
- 리뷰가 필요한 위험이나 미검증 항목

사용자가 변경을 리뷰할 수 있도록 로컬 diff를 유지한다. 사용자가 사전에 현재 Task 또는 명확한 Task 묶음의 커밋까지 승인하지 않았다면 커밋 전에 사용자 리뷰와 승인을 기다린다. 수정 요청은 같은 Task에 반영하고 다시 검증한다.

## 커밋과 종료

승인 범위가 분명하면 같은 범위에 대한 확인을 반복하지 않는다. 관련 코드, 테스트, spec, plan과 Task 완료 표시만 명시적으로 stage해 같은 커밋에 포함한다. 커밋에는 `commit-changes`의 원자성, 메시지와 공급망 검사를 적용한다.

커밋 결과와 검증 근거를 보고하고 종료한다. 현재 Task가 커밋되기 전이나 커밋 직후에 다음 Task를 시작하지 않는다. 다음 Task는 사용자의 새 요청이나 이미 명시된 일괄 실행 범위가 있을 때 별도로 시작한다.
