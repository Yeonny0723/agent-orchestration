# 작업 오케스트레이션

## 목적

현재 코드와 문서를 조사해 기능 목표와 사용자 Use Case를 먼저 담은 living spec 초안을 만든다. 사용자의 비판을 받아 설계를 반복 검토하고 범위를 좁힌 다음 Task 계획을 세운다. 구현 중 발견한 사실도 같은 문서에 반영한다.

초기 Spec 작성 요청은 이 절차를 기본 설계 대화로 취급한다. 다른 선택형 brainstorming 도구의 별도 승인 단계나 문서 생성 규칙을 추가해 이 순서를 바꾸지 않는다.

작고 명확한 작업에서는 별도 spec이나 plan이 주는 가치가 낮으면 생략할 수 있다.

Spec 깊이는 변경 규모에 맞춘다. 사용자 흐름이 여러 개이거나, 여러 구성요소·외부 시스템이 함께 바뀌거나, 새로운 공개 API·저장 데이터·도메인 관계·비동기 처리가 생기는 작업은 상세 Spec 대상으로 본다. 한 모듈 안의 명확한 동작 수정처럼 계약·데이터 구조·시스템 경계가 바뀌지 않는 작은 작업에는 아래 다이어그램과 상세 스키마를 요구하지 않는다. 적용하지 않은 산출물이 중요한 검토를 빠뜨리는지 확인하고, 필요하면 생략 이유만 짧게 기록한다.

## 조사

작업 결과에 영향을 주는 범위에서 현재 구조, 공개 계약, 기존 결정과 변경 이력을 확인한다. 조사 범위와 깊이는 에이전트가 판단한다.

기능 목표와 성공 기준을 먼저 정리한 뒤, 사용자 인터페이스에서 사용자가 시작할 수 있는 Use Case를 폭넓게 찾는다. Use Case 검토는 핵심 단계다. 각 흐름에서 정상 동작과 예외를 구분하고, 현재 구조와 제약을 근거로 실현 가능성·영향·운영 위험을 설명한다. 다음 관점 중 실제 작업에 관련된 항목을 검토한다.

상세 Spec 대상이면 아래 설계 산출물을 작성한다. 다이어그램과 스키마는 아직 확정되지 않은 제안을 사실처럼 표현하지 말고 결정 상태를 분명히 한다.

- **Use Case 다이어그램:** 행위자, 시스템 경계와 주요 사용자 Use Case를 나타낸다. 텍스트로 정의한 Use Case 및 MVP 포함·후순위·제외 범위와 일치시킨다.
- **Flow chart:** 사용자 동작부터 구성요소 간 요청·응답, 주요 분기와 실패·복구까지 핵심 end-to-end 흐름을 나타낸다. 시스템 경계와 책임 주체가 중요하면 swimlane을 사용한다.
- **API 계약:** 새로 만들거나 바뀌는 API의 호출자·제공자, method/path, 요청·응답 schema와 예시, 상태 코드·오류 형식, 인증·제한·재시도 정책을 정리한다. 공개 계약과 내부 API를 구별한다.
- **DB schema / ERD:** 엔티티, 필드와 타입, PK·FK, 관계·카디널리티, 제약·인덱스, 보존 정책을 적는다. 기존 엔티티 재사용 여부, migration 영향과 확인하지 못한 물리 DB 차이를 표시한다.
- **Class diagram:** 객체·서비스 책임, 핵심 속성·행위와 관계가 도메인 이해나 구현 경계에 도움이 될 때 작성한다. DB ERD와 혼동하지 않는다. 두 관점이 모두 중요하면 둘 다 표현한다.
- **PoC 중심 작업 우선순위:** 핵심 사용자 가치를 가장 빨리 보여 주는 작은 수직 슬라이스를 P0로 두고, 선행 의존성·담당 역할·완료 기준을 함께 적는다. 후속 범위는 P1/P2 또는 후순위로 나눈다. PoC가 부적합한 작업은 이유를 남기고 위험 감소나 필수 의존성부터 우선한다.

다이어그램 작성에는 연결된 경우 Draw.io MCP를 사용한다. Mermaid를 지원하는 flow chart·ERD·Class diagram은 `open_drawio_mermaid`를, UML Use Case나 Mermaid로 표현하기 어려운 그림은 `open_drawio_xml`을 사용할 수 있다. 기존 `.drawio` 파일은 `list_pages`와 `get_page`로 페이지를 확인한 뒤 `set_page`로 수정한다. 사용자 Use Case, Flow chart, ERD와 Class diagram은 편집 가능한 `.drawio` 원본으로 관리하고, Spec 본문에서 바로 볼 수 있는 PNG도 같은 문서 폴더에 내보내 상대 경로로 삽입한다. 한 Draw.io 파일에 여러 페이지를 두어도 된다. MCP가 파일 저장·PNG 내보내기를 지원하지 않는 환경에서는 가능한 편집·내보내기 경로를 쓰고, 실제로 생성하지 못한 산출물을 완료된 것처럼 표시하지 않는다.

- 상태와 데이터 소유권
- 시스템 사이의 입력과 출력
- 오류, 재시도와 부분 실패
- 크기, 비용, 성능과 자원 제한
- 로그와 운영 위험
- 보안, 개인정보와 호환성
- 구성요소별 책임과 복잡도를 줄이는 대안

## 초안 작성

`templates/spec.md`를 기본 구조로 사용한다. 초안은 기능 목표와 사용자 Use Case부터 작성하며 Task 계획은 설계 검토와 범위 좁히기가 끝난 뒤 작성한다. Task 계획은 별도 plan이 필요하지 않으면 living spec에 둔다. 가독성이나 독립 작업 경계 때문에 유리할 때만 plan을 분리한다.

사용자에게 검토받을 문서가 준비되면 `author-reviewable-text`에 산출물 종류, 확인된 사실, 필수 형식, 해당되는 길이 제한을 전달한다. 반환된 초안을 저장하고 사용자 리뷰를 요청한다.

## 반복 검토

사용자의 질문과 설계 비판에 답하고 같은 living spec과 연결 다이어그램을 함께 갱신한다. 사용자가 이해되지 않는 부분이나 설계 결함을 지적하면 근거를 확인해 답하고, 필요하면 관련 설계와 문서를 고친다. 남은 중요한 비판이나 설계 빈칸이 없을 때까지 이 검토를 반복한다. 질문의 수와 표현은 에이전트가 판단하되 목표·Use Case → 예외·운영 위험·구조 제약 → 범위 축소·결정 정리 순서를 지킨다. 불필요하거나 가치가 낮은 Use Case는 MVP에서 제외하거나 후순위로 돌려 복잡도를 낮춘다. API, DB, 다이어그램, 우선순위 간 불일치가 없는지 함께 확인한다. 영향이 큰 빈칸을 더 깊게 검토할 때 `decision-first-grill`을 선택할 수 있다.

결정에는 필요한 경우 `검토 중`, `잠정 결정`, `확정`, `후순위` 상태를 표시한다. MVP 제외 항목은 결정 상태와 분리한다. 결정이 바뀌면 이유와 API 계약, 구현 및 Task 계획에 미치는 영향을 함께 맞춘다.

각 Use Case의 MVP 포함, 후순위 또는 제외 여부를 정리하고, 관련 예외·운영 위험·현재 구조와 제약을 검토한다. 미해결 항목에는 `검토 중`, `잠정 결정`, `확정`, `후순위` 중 적절한 상태와 현재 범위에 미치는 영향을 기록한다. 반복 비판에서 더 다룰 중요한 쟁점이 남지 않으면 Task 계획을 작성하고, 목표부터 계획까지 사용자가 최종 리뷰·승인한 뒤 spec을 완료 기준본으로 확정한다. 현재 범위를 막지 않는 미결정은 상태와 영향을 명시해 남길 수 있다.
