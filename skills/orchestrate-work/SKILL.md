# 작업 오케스트레이션

## 목적

현재 코드와 문서를 조사해 첫 living spec과 간결한 Task 체크리스트를 만든다. 초안은 사용자와 반복 검토하며 발전시키고, 구현 중 발견한 사실도 같은 문서에 반영한다.

작고 명확한 작업에서는 별도 spec이나 plan이 주는 가치가 낮으면 생략할 수 있다.

## 조사

작업 결과에 영향을 주는 범위에서 현재 구조, 공개 계약, 기존 결정과 변경 이력을 확인한다. 조사 범위와 깊이는 에이전트가 판단한다.

사용자 입력에서 시작하는 정상 Use Case와 예외 흐름을 찾는다. 다음 관점 중 실제 작업에 관련된 항목을 검토한다.

- 상태와 데이터 소유권
- 시스템 사이의 입력과 출력
- 오류, 재시도와 부분 실패
- 크기, 비용, 성능과 자원 제한
- 로그와 운영 위험
- 보안, 개인정보와 호환성
- 구성요소별 책임과 복잡도를 줄이는 대안

## 초안 작성

`templates/spec.md`를 기본 구조로 사용한다. 별도 plan이 필요하지 않으면 Task 체크리스트를 living spec에 둔다. 가독성이나 독립 작업 경계 때문에 유리할 때만 plan을 분리한다.

사용자에게 검토받을 문서가 준비되면 `author-reviewable-text`에 산출물 종류, 확인된 사실, 필수 형식, 해당되는 길이 제한을 전달한다. 반환된 초안을 저장하고 사용자 리뷰를 요청한다.

## 반복 검토

사용자의 질문과 설계 비판에 답하고 같은 living spec을 갱신한다. 필요한 질문의 수, 순서와 형식은 에이전트가 판단한다. 영향이 큰 빈칸을 더 깊게 검토할 때 `decision-first-grill`을 선택할 수 있다.

결정에는 필요한 경우 `검토 중`, `잠정 결정`, `확정`, `후순위` 상태를 표시한다. MVP 제외 항목은 결정 상태와 분리한다. 결정이 바뀌면 이유와 API 계약, 구현 및 Task 계획에 미치는 영향을 함께 맞춘다.

발견한 Use Case가 MVP 포함, 후순위 또는 제외로 정리되고 관련 예외와 운영 위험을 검토한 뒤 사용자가 기준본을 승인하면 초기 spec을 커밋할 수 있다. 아직 좁혀지지 않은 항목은 상태와 영향을 명시한다.

## 다음 단계

기준본 이후에는 사용자가 지정한 Task만 실행한다. Task 수행은 `execute-task`가 담당하며 이 skill은 구현, 검증, 커밋과 PR 절차를 고정하지 않는다.
