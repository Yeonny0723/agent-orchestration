# 작업 오케스트레이션

## 목적과 기준

현재 코드와 사용자 리뷰를 근거로 같은 living spec을 발전시키고, 설계 검토와 범위 축소가 끝난 뒤 Task 계획을 만든다. 작고 명확한 작업에서 별도 spec이나 plan의 가치가 낮으면 생략할 수 있다.

초기 Spec 작성 요청은 이 절차를 기본 설계 대화로 취급한다. 다른 선택형 brainstorming 도구의 별도 승인 단계나 문서 생성 규칙을 추가해 이 순서를 바꾸지 않는다.

시작할 때 [Spec 템플릿](../../templates/spec.md)을 읽는다. 적용 깊이, 필수 내용, 표기와 완료 기준은 템플릿을 따른다. [완성 샘플 해설](../../examples/spec/document-generation/README.md)은 표현 수준을 확인할 때 읽고, 그림을 만들거나 고칠 때 [다이어그램 작성 지침](references/diagrams.md)을 읽는다. 샘플의 제품 결정을 현재 작업의 요구사항으로 사용하지 않는다.

## 조사

작업 결과에 필요한 현재 구조, 공개 계약, 기존 결정과 변경 이력을 확인한다. 조사 범위와 깊이는 에이전트가 판단한다. 기능 목표와 성공 기준을 먼저 정리하고, 사용자 인터페이스에서 시작할 수 있는 Use Case를 폭넓게 찾는다.

정상 동작·예외 흐름의 실현 가능성, 현재 구조의 제약과 운영 위험을 근거로 설명한다. [검토 질문](references/workflow.md)을 필요에 따라 사용한다.

## 초안 작성

템플릿을 현재 작업에 적용해 기능 목표와 사용자 Use Case부터 작성한다. Task 계획은 설계 검토와 범위 좁히기가 끝난 뒤 작성한다. 별도 plan은 가독성이나 독립 작업 경계에 유리할 때만 분리한다.

사용자에게 검토받을 문서가 준비되면 `author-reviewable-text`에 산출물 종류, 확인된 사실, 템플릿에서 적용한 필수 형식, 해당되는 길이 제한을 전달한다. 반환된 초안을 저장하고 사용자 리뷰를 요청한다.

## 반복 검토

사용자의 질문과 설계 비판에 근거로 답하고 같은 living spec을 갱신한다. 목표·Use Case → 예외·운영 위험·구조 제약 → 범위 축소·결정 정리 순서로 검토한다. 중요한 반론이나 설계 빈칸이 남으면 검토를 이어간다. 영향이 큰 가정을 더 깊게 검토할 때 `decision-first-grill`을 선택할 수 있다.

결정 변경은 템플릿의 갱신 규칙에 따라 관련 계약·그림·Task에 반영한다. 현재 범위를 막지 않는 미결정은 영향과 함께 남길 수 있다.

## 계획과 최종 리뷰

설계의 중요한 빈칸과 불필요한 범위를 정리한 뒤 Task 계획을 작성한다. 템플릿의 완료 기준으로 Spec 전체의 정합성을 자체 확인하고, 목표부터 계획까지 사용자가 최종 리뷰·승인한 뒤 완료 기준본으로 확정한다.

## 다음 단계
