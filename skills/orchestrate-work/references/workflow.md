# Living spec 검토 관점

초기 spec 검토는 아래 순서로 진행한다. 각 항목의 깊이는 작업에 맞춘다. 여러 사용자 흐름·구성요소·외부 연동·신규 API/저장 데이터가 얽힌 큰 변경은 상세 산출물을 만든다. 계약과 데이터 경계가 변하지 않는 작은 변경은 간략하게 처리하고 상세 설계 산출물을 생략할 수 있다. 목표와 사용자 Use Case를 먼저 다루고 Task 계획은 검토와 범위 축소가 끝난 뒤 작성한다.

1. 기능 목표와 성공 기준
2. 사용자 인터페이스에서 가능한 Use Case의 폭넓은 탐색 및 MVP 범위 지정
3. 예외 흐름, 운영 위험, 현재 구조와 제약
4. 큰 변경이면 Draw.io 기반 설계 그림, API 계약, DB schema/ERD, 필요 시 Class diagram
5. 결정 상태와 불필요한 범위 제거
6. PoC 또는 위험 감소를 앞세운 작업 우선순위와 Task 계획
7. spec 전체와 연결 시각 자료의 최종 리뷰 및 사용자 승인

## 큰 변경의 설계 산출물

- **Use Case diagram:** 사용자/외부 행위자, 시스템 경계, 주 흐름과 선택 기능. 각 Use Case의 MVP 범위는 본문과 일치시킨다.
- **Flow chart:** 핵심 end-to-end 흐름, 시스템 간 전달, 조건 분기와 실패·복구 흐름. 책임 경계를 보일 때 swimlane을 쓴다.
- **API schema:** method/path, caller/provider, request/response 형식, 오류·상태 코드와 예시. 공개 API와 내부 API를 구분하고 미확정 계약은 제안으로 표시한다.
- **DB schema / ERD:** 엔티티·필드·타입·PK/FK·관계·제약·인덱스·보존 정책 및 기존 테이블 재사용과 migration 영향.
- **Class diagram:** 도메인 객체·서비스의 책임, 속성과 관계가 설계를 설명하는 데 도움이 될 때 작성한다. DB ERD를 대신하지 않는다.
- **우선순위:** P0은 핵심 가치를 보여주는 최소 수직 PoC와 꼭 필요한 선행 의존성, P1/P2는 후속 개선으로 구성한다. 작업별 담당, 의존성, 완료 기준을 적고 PoC 접근이 맞지 않으면 이유를 기록한다.

Draw.io MCP가 연결돼 있으면 다이어그램을 생성·수정한다. Mermaid를 지원하는 flow chart·ERD·Class diagram은 `open_drawio_mermaid`, UML Use Case나 Mermaid로 표현하기 어려운 그림은 `open_drawio_xml`을 쓸 수 있다. 기존 파일은 `list_pages`와 `get_page`로 페이지를 확인하고 `set_page`로 갱신한다. 편집 가능한 `.drawio` 원본과 본문에서 미리 볼 PNG를 Spec과 가까운 폴더에 저장하고 상대 경로로 연결한다. 저장 또는 PNG 내보내기를 수행하지 못하면 그 사실을 밝히고 산출물을 완료된 것으로 취급하지 않는다.

사용자의 비판을 받아 중요한 설계 빈칸이나 반론이 더는 남지 않을 때까지 같은 living spec을 반복 갱신한다. 모든 미결정을 억지로 확정하지 않는다. 현재 범위에 영향을 주지 않는 미결정은 상태와 영향으로 표시한다.

## 기능과 입력 경계

- 사용자가 달성하려는 결과와 선언된 입력 경계는 무엇인가?
- 정상, 빈 입력, 잘못된 입력, 중복, 취소와 재시도는 어떻게 보이는가?
- 각 Use Case는 MVP 포함, 후순위 또는 제외 중 어디에 속하는가?
- 사용자 인터페이스에서 시작할 수 있는 관련 Use Case를 빠뜨리지 않았는가? 각 흐름의 가치와 복잡도를 비교해 불필요한 경우를 줄였는가?

## 상태와 데이터 흐름

- 상태를 누가 만들고 보관하며 폐기하는가?
- 구성요소 사이에서 전달되는 필드와 응답 형태는 무엇인가?
- 부분 성공이나 오래된 상태를 어떻게 다루는가?

## 운영 경계

- 응답 크기, 비용, 지연과 자원 제한은 어디에서 통제하는가?
- 오류를 누구에게 어떤 형태로 전달하며 재시도와 복구 책임은 어디에 있는가?
- 요청, 대화와 비용을 구분하기 위한 로그 식별자는 무엇인가?
- 운영 정책이 필요하면 기능 플래그, timeout, 재시도 횟수, 토큰·크기 한도와 비용 기준은 무엇인가?
- 프로젝트 안에서 기능·데이터·운영의 책임과 비용 소유권은 누구에게 있는가?
- 우선순위에서 핵심 가치를 입증하는 최소 PoC와 그 선행 의존성이 먼저 보이는가?

## 결정 정합성

결정이 바뀌면 같은 living spec의 계약, Task 계획과 연결 다이어그램을 함께 갱신한다. 아직 답을 알 수 없는 항목은 상태와 현재 작업에 미치는 영향을 기록한다. 설계 검토가 끝난 뒤에만 Task 계획을 작성하며, 마지막에는 기능 목표·Use Case·다이어그램·API/DB schema·예외·결정·계획 사이의 정합성을 포함해 사용자가 Spec 전체를 리뷰한다.
