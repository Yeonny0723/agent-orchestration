# 의사결정 그릴

## 준비

현재 구조를 근거로 작성된 living spec 초안과 관련 코드를 읽는다. [Spec 템플릿](../../templates/spec.md)을 내용·표기·완료 기준으로 사용한다. 기능 목표와 사용자 Use Case를 먼저 검토하고, [검토 질문](../orchestrate-work/references/workflow.md)으로 예외와 운영 위험 등 결과를 바꾸는 설계 빈칸을 찾는다. 적용 깊이와 생략 판단도 템플릿을 따른다.

설치돼 있으면 `grill-with-docs`를 인터뷰에, `domain-modeling`을 여러 작업에서 공유할 용어나 ADR 후보 정리에 활용할 수 있다. 두 skill이 설치되지 않아도 이 검토를 계속한다.

## 질문 루프

1. 목표와 각 Use Case가 사용자 가치에 맞는지, MVP에서 불필요한 범위를 줄일 수 있는지 검토한다.
2. 현재 결정이나 설계의 가정을 구체적인 정상 또는 예외 상황으로 검증하고 구조 제약 및 운영 위험을 설명한다.
3. 사용자 선택에 따라 제품 행위, 공개 계약, 범위나 책임이 달라지는 빈칸을 질문한다.
4. 선택이 필요하면 상호 배타적인 선택지, 트레이드오프, 추천안과 이유를 제시한다.
5. 답변에 따라 같은 living spec의 결정 상태와 영향을 갱신한다.
6. 중요한 비판이나 설계 빈칸이 남아 있으면 검토를 계속한다. 변경은 템플릿의 정합성·갱신 규칙에 따라 반영하고, 그림이 바뀌면 [다이어그램 작성 지침](../orchestrate-work/references/diagrams.md)을 따른다. 더 검토할 중요한 쟁점이 없을 때 설계 검토를 마치고 이후 Task 계획을 작성하도록 한다.

질문 개수는 고정하지 않지만 목표·Use Case 탐색을 먼저 하고 검토와 복잡도 축소를 Task 계획보다 앞에 둔다. 모든 가능한 미래 상황을 열거했다고 주장하지 않는다. 선언한 사용자 인터페이스와 범위에서 검토하고, 지금 답을 모르는 항목은 템플릿의 결정 상태와 영향으로 남긴다.

## 기록 위치

결정 배경, 이유와 API·구현·Task 계획에 미치는 영향은 living spec에 둔다. 단순 작업 메모를 ADR로 만들지 않는다.

## spec 작성

설계 검토가 끝난 뒤 Task 계획을 작성하고, 검토 결과를 반영한 문서를 제시할 때 `author-reviewable-text`에 산출물 종류, 확인된 사실, 템플릿에서 적용한 필수 형식과 해당되는 길이 제한을 전달한다. 반환된 living spec 전체의 사용자 리뷰와 승인을 받는다. 승인된 spec을 완료 기준본으로 삼으며, 남은 미결정의 영향과 정합성은 템플릿의 완료 기준으로 확인한다.
