# 작업 이해 세션

## 호출과 책임

사용자 명시적 호출이 있을 때만 시작한다. 구현이나 PR을 자동으로 막는 게이트가 아니며 PR을 차단하지 않는다. 파일, 등록부, 정답지, 점수 또는 영구 학습 기록을 만들지 않고 질문과 피드백을 현재 대화에만 남긴다.

## 근거 수집

승인된 spec, 현재 실제 diff, 연결된 이슈와 ADR, 변경과 직접 관련된 문서를 읽는다. `references/question-design.md`를 적용하고 필요하면 읽기 전용 `work-question-designer` agent로 후보를 생성한다.

질문 전에 잘못 이해하면 유지보수 판단을 그르칠 핵심 주장, 결정, 불변식, 경계와 실패 지점을 전수 목록화한다. 그다음 위험도와 유지보수 중요도로 순위를 매긴다. 주장마다 질문을 만들지는 않는다.

## 다섯 이해 축

1. 사양 설명: 해결하는 문제, 기대 동작과 비목표를 설명할 수 있는가.
2. 구조와 실행 흐름: 요청, 데이터 또는 상태가 거치는 구성요소를 설명할 수 있는가.
3. 핵심 결정과 제약: 선택 이유와 변경 시 지킬 경계를 아는가.
4. 문제 진단과 변경 위치: 증상 발생 시 어느 파일, 모듈 또는 계약부터 확인할지 아는가.
5. 검증과 영향 범위: 어떤 테스트가 행위를 보장하고 어디까지 영향을 확인할지 아는가.

실제 근거가 있는 축에서 최대 5문항을 선정한다. 질문 하나에는 판단 하나만 둔다.

## 질문 작성

선정한 각 질문을 사용자에게 보여주기 전에 `author-reviewable-text`에 산출물 종류가 `understand-work` 질문임을 밝히고 질문의 필수 형식, 판단 대상과 관련 근거인 확인된 사실, 질문 길이 제한과 필요한 선택지를 전달한다. 반환된 문구를 질문에 사용하되 판단 하나만 묻는 계약은 유지한다. 답변 뒤의 기술적 피드백, 근거 설명과 마지막 이해 요약에는 공통 작성 skill을 적용하지 않는다.

## 진행

1. 선정한 질문을 한 번에 하나씩 묻는다.
2. 답변마다 이해한 부분, 혼동하거나 빠뜨린 부분, 보완 설명과 근거 위치를 제공한다.
3. 이전 답변에 맞춰 아직 묻지 않은 질문을 조정할 수 있지만 총 문항 수를 늘리지 않는다.
4. 충분하다고 자율 종료하지 않고 선정한 질문을 모두 묻는다.
5. 마지막에 이해한 영역과 보완할 영역을 대화로 요약한다.
