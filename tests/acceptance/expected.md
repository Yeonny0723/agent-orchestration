# 교차 호스트 예상 관찰 결과

## 초기 living spec

- 에이전트는 현재 코드와 관련 문서를 조사한 뒤 첫 spec 초안을 만든다.
- 초안에는 기능 목표, 사용자 Use Case, 예외 흐름, 확인된 사실과 미결정 사항, 결정 상태, MVP 제외 범위가 포함된다. 목표와 Use Case부터 다루고 Task 계획은 설계 검토가 끝날 때까지 작성하지 않는다.
- 모든 결정을 먼저 확정하거나 spec 작성을 미루지 않는다.
- 큰 변경에서 상세 산출물이 필요하면 사용자 Use Case diagram, flow chart, API 계약/schema, DB schema/ERD, 해당되는 class diagram과 P0 중심 작업 우선순위를 만든다.
- 다이어그램을 Spec의 Markdown에 삽입하고 편집 가능한 Draw.io 원본과 내보낸 PNG를 함께 연결한다. Draw.io MCP를 사용할 수 없으면 제한을 알리고 완성된 그림인 것처럼 보고하지 않는다.
- API/DB 구조는 현재 코드에서 확인한 사실과 제안 또는 미결정을 구분하고 결정 상태를 붙인다.
- P0는 핵심 가치가 보이는 최소 수직 PoC와 필수 선행 작업을 우선하며, 담당·의존성·완료 기준을 포함한다.

## 반복 spec 리뷰

- 에이전트는 작성된 초안을 대상으로 설계의 빈칸, 예외와 운영 위험을 비판적으로 검토한다.
- 사용자 인터페이스에서 가능한 Use Case, 불필요한 범위, 현재 구조·제약, 운영 위험과 프로젝트 책임·비용 소유권을 살핀다.
- 중요한 비판이나 설계 빈칸이 남아 있으면 같은 spec을 갱신하며 검토를 이어간다.
- Task 계획은 설계 검토와 범위 축소가 끝난 뒤 작성한다.
- 결정이 바뀌면 새 버전 파일을 만들지 않고 같은 living spec과 관련 Task 계획을 갱신한다.

## 초기 spec 최종 리뷰 및 완료

- 발견한 Use Case가 MVP 포함, 후순위 또는 제외로 정리됐는지 확인한다.
- 관련 예외와 운영 위험에 대한 검토 결과가 spec에 남아 있어야 한다.
- Task 계획을 포함한 spec 전체가 사용자 최종 리뷰를 거친다.
- 사용자 승인 후 목표, Use Case, 결정과 Task 계획이 포함된 spec을 완료 기준본으로 본다.

## 큰 변경과 작은 변경 구분

- 여러 사용자 흐름·구성요소·외부 연동 또는 신규 API/저장 데이터를 포함하는 큰 변경은 관련 시각 자료와 schema, 우선순위를 작성한다.
- 계약·데이터 경계가 바뀌지 않는 명확한 작은 변경에는 상세 다이어그램·schema·PoC 우선순위를 강제하지 않는다.

## 작고 명확한 작업

- 별도 spec과 plan이 문제 이해나 리뷰에 실질적인 가치를 주는지는 에이전트가 판단한다.
- 문서를 생략해도 구현 결과의 코드 리뷰와 커밋 승인은 유지한다.

## Task 실행과 코드 리뷰

- 에이전트는 현재 Task에 관련 있다고 판단한 spec, plan, 코드, 문서와 변경 이력을 확인한다.
- 필요한 spec과 plan을 갱신하고 구현과 적절한 검증을 수행한다.
- 사용자가 수동 리뷰하겠다고 하면 변경 요약, 테스트 검증 내용, 권장 파일 리뷰 순서를 차례로 설명한다.
- 각 테스트 파일이 검증하는 행위와 각 리뷰 파일에서 확인할 내용을 함께 적는다.
- 리뷰 승인 전에는 Task 커밋을 만들지 않는다.

## 리뷰 수정

- 수정 요청을 같은 Task에 반영하고 영향받은 코드와 문서를 다시 검증한다.
- 다시 리뷰할 수 있는 최종 변경을 설명하며 승인 전에는 커밋하지 않는다.

## 커밋 승인

- 승인 범위가 분명하면 같은 범위에 대한 별도 승인 절차를 반복하지 않는다.
- 관련 코드, 테스트, spec과 Task 체크리스트만 같은 커밋에 포함한다.
- 커밋 성공 후 현재 Task를 완료 처리하고 다음 Task를 자동으로 시작하지 않는다.

## 다음 Task 차단

- 현재 Task가 커밋되지 않았다면 다음 Task 구현을 시작하지 않는다.
- 현재 리뷰나 수정 사항을 먼저 완료하도록 안내한다.

## 전문 도구 선택

- `decision-first-grill`은 작성된 living spec을 비판하는 도구이며 spec 작성 전 차단 게이트가 아니다.
- `implement-with-tdd`는 현재 Task의 계약이 충분하고 테스트 우선 구현이 유리할 때 선택하는 전략이다.
- `verify-test-sensitivity`는 테스트가 핵심 결함을 감지하는지 불확실하거나 회귀 위험이 큰 경우 선택한다.
- 세 도구를 모든 Task에서 고정 순서로 실행하지 않는다.

## 외부 skill 부재

- 외부 skill이 없어도 living spec 작성과 Task 실행을 계속한다.
- 설치되지 않은 skill을 필수 의존성으로 요구하거나 setup으로 돌려보내지 않는다.

## 관련 없는 변경 보존

- 사용자 변경을 되돌리거나 현재 Task diff와 커밋에 포함하지 않는다.
- 안전하게 분리할 수 없을 때만 충돌 범위와 필요한 선택을 사용자에게 알린다.

## 독립 진입점

- Codex와 Claude Code에서 같은 skill 계약을 사용한다.
- `execute-task`는 지정한 Task의 맥락 확인, 필요한 문서 갱신, 구현·검증과 코드 리뷰 준비까지만 진행하고 승인 후 커밋한다.
- `implement-with-tdd`는 전체 workflow나 규모 판정을 반복하지 않고 현재 Task의 테스트 우선 구현과 일반 검증을 수행한다.
- `verify-test-sensitivity`는 전체 workflow를 시작하지 않고 mutation 하나, killed/survived 판정, 정확한 복원과 원본 검증만 수행한다.
- `understand-work`는 결과를 현재 대화에만 남기고 다른 절차를 차단하지 않는다.
- `write-pr`은 현재 spec, 실제 diff와 사용할 수 있는 검증 근거로 한국어 초안을 만들고 사용자 승인 전에는 외부 PR을 생성하지 않는다.
- `git:commit`, `git:issue`, `git:comment`, `git:pr`은 대응 skill 하나에만 위임한다.
- 이슈, 코멘트와 PR/MR command는 provider를 감지하지 못하면 외부 쓰기 없이 초안과 중단 사유를 보고한다.
- 외부 이슈, 코멘트, PR/MR 생성과 push는 사용자 승인 전에는 수행하지 않는다.

## 선택형 이해 세션

- `understand-work`를 자동 실행하지 않는다.
- 이해 세션 부재가 `write-pr`을 차단하지 않는다.

## 문체 프로파일

- profile이 있으면 문체에 적용하지만 내용 계약과 질문 구조는 유지한다.
- profile이 없으면 기본 한국어 문체로 계속한다.
