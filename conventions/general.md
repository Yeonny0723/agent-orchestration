# 일반 코드 컨벤션

## 범위와 문제 해결

- 요청한 범위만 변경하고 관련 없는 리팩터링을 섞지 않는다.
- 확인되지 않은 요구나 구조를 추정해 확정하지 않는다.
- 증상만 가리는 수정 대신 재현 가능한 근본 원인을 확인한다.
- 재사용할 prompt나 skill 지침은 현재 테스트 예시에 종속시키지 말고 같은 종류의 문제에 적용되도록 일반화한다.

## 외부 경계

- 외부 API, 라이브러리, SDK, 데이터베이스, ORM과 파일 형식은 adapter, wrapper 또는 gateway 경계에서 내부 형태로 변환한다.
- 외부 response, 타입과 데이터 구조를 비즈니스 로직이나 도메인 모델 전체로 전파하지 않는다.
- 내부 코드는 특정 외부 구현 대신 추상화된 내부 인터페이스에 의존한다.
- 외부 API, SDK, 데이터베이스, ORM, 파일 형식, 메시지 브로커, 프레임워크, 인증·결제 서비스 또는 아직 확정되지 않은 인터페이스가 있으면 경계 도입을 우선 검토한다.

## 용어집과 네이밍

- 대상 프로젝트에 `CONTEXT.md`, `UBIQUITOUS_LANGUAGE.md`, `docs/glossary/` 또는 이에 준하는 용어집이 있으면 코딩 전에 먼저 읽는다.
- 용어집에 정의된 canonical term을 클래스, 함수, 변수, 타입, API 필드, 테스트 이름과 사용자에게 보이는 문구의 기준 이름으로 사용한다.
- 같은 개념에 임의의 동의어, 번역어 또는 약어를 새로 만들지 않는다. 기존 코드의 비일관적인 이름을 바꿀 때는 변경 범위와 호환성 영향을 확인한다.
- 용어집의 정의가 서로 충돌하거나 필요한 개념이 정의되지 않았으면 임의로 확정하지 말고 사용자에게 결정 사항으로 질문한다. 확정된 용어는 해당 프로젝트의 용어집 또는 결정 문서에 반영한다.

### 도메인 역할 중심의 이름

- 변수와 함수 이름은 자료형보다 도메인 역할과 사용 목적을 표현한다.
- `index`, `element`, `data`, `item`, `anchor`처럼 문맥만으로 대상을 알 수 없는 이름을 피한다.
- 대상과 역할 또는 결과를 함께 명시한다. 예를 들어 `table_shape_index`, `cloned_row_element`, `insertion_anchor_unit`, `insert_after`처럼 이름만 읽어도 무엇을 가리키고 어디에 사용하는지 알 수 있어야 한다.
- 목록의 위치, 요소의 자료형 또는 임시 데이터라는 이유만으로 일반적인 이름을 사용하지 않는다.

### 변환 함수와 기준점 이름

- 좌표나 값을 변환하는 함수는 함수명에 변환 결과와 방향을 명시한다.
- 인자명에는 입력 값의 기준과 역할을 표현한다.
- `row`, `edits`, `index`처럼 기준이 불분명한 이름을 피하고, `original_row_index`, `current_row_index`, `row_edit_history`처럼 원본·현재·이력의 의미를 구분한다.
- 함수 이름만으로 입력과 출력의 관계와 변환 방향을 유추할 수 있어야 한다. 예를 들어 `current_row_index_from_original_row_index`, `transform_relative_target_to_absolute`처럼 변환 결과와 입력 기준을 드러낸다.

### Docstring 작성 기준

- 이름만으로 함수의 역할과 사용 목적을 충분히 유추할 수 없는 경우에만 docstring을 작성한다.
- docstring을 추가하기 전에 함수명을 먼저 명확하게 개선한다.
- 함수명을 개선한 뒤에도 현재 함수의 존재 이유, 호출 맥락 또는 어느 호출 경로에서 사용되는지가 드러나지 않을 때만, 왜 필요한지와 어떤 판단에 사용되는지를 설명한다.
- 함수의 코드 내용을 그대로 반복하는 docstring은 작성하지 않는다.

### 함수 이름의 동작 접두어

함수 이름의 접두어는 표기 방식보다 함수의 동작 의미를 기준으로 선택한다. 언어의 일반적인 네이밍 규칙을 따르며, Python에서는 `snake_case`, JavaScript와 TypeScript에서는 `camelCase`를 사용한다.

| 의미 | Python 예시 | JavaScript/TypeScript 예시 |
|---|---|---|
| 조건 판단 | `is_valid` | `isValid` |
| 유효성 검증 | `validate_row` | `validateRow` |
| 메모리 내 값 조회 | `get_current_row` | `getCurrentRow` |
| 외부 저장소에서 읽기 | `load_document` | `loadDocument` |
| 외부 저장소에 쓰기 | `save_document` | `saveDocument` |
| 값 직접 지정 | `set_status` | `setStatus` |
| 기존 상태 갱신 | `update_row` | `updateRow` |
| 연산·규칙 적용 | `apply_row_edit` | `applyRowEdit` |
| 생성 | `create_report` | `createReport` |
| 삭제 | `delete_row` | `deleteRow` |
| 형식 변환 | `transform_to_table_shape` | `transformToTableShape` |
| 작업 실행 | `execute_import` | `executeImport` |

- 위 접두어는 의미가 정확히 일치할 때만 사용한다.
- 접두어만으로 함수의 대상과 역할이 드러나지 않으면 도메인 대상을 이름에 함께 명시한다. `get_data`보다 `get_current_row` 또는 `getCurrentRow`가 적절하다.
- 위 목록에 해당하지 않는 함수는 자료형이 아니라 도메인 동작을 표현하는 동사를 사용한다. 예를 들어 `insert_after` 또는 `insertAfter`, `reconcile_row_edits` 또는 `reconcileRowEdits`처럼 작성한다.
- 함수명은 해당 언어의 관례에 맞게 작성하되, 변환 방향과 부작용은 이름만으로 유추할 수 있어야 한다.
- 부작용이 있는 함수는 상태 변경이나 외부 작업을 함수명에 명시한다. 조회처럼 보이는 이름으로 객체를 수정하지 않는다. `get_*`, `validate_*`, `transform_*`, `create_*`, `apply_*`는 실제 역할에 맞게 구분한다.

### 조건과 반복 로직의 의도 표현

- 복잡한 조건은 의미 있는 Boolean 변수나 함수로 분리한다. `isinstance(...)` 같은 조건이 길게 반복되면 `is_table_replacement`처럼 판단 의도를 표현한다.
- 복잡한 comprehension은 중간 변수로 풀어 쓴다. 여러 반복문과 조건이 결합되면 입력, 선택 기준, 결과가 각각 드러나도록 단계별 변수와 구문으로 분리한다.

### 계약 일관성과 입력 경계

- DTO·프롬프트·서비스에서 같은 개념은 같은 용어를 사용한다. 계약 용어를 변경할 때 일부 계층만 바꾸지 않는다.
- 계약 필드명을 변경하면 DTO, prompt, parser, compiler, writer, 테스트, 문서의 전체 호출 흐름을 검색하고 함께 갱신한다.
- 입력 경계에서 무효한 값은 조기에 거부한다. 음수 좌표, 빈 삭제 목록, 개수가 다른 병렬 목록 등을 렌더러나 하위 처리 단계까지 넘기지 않는다.
- 병렬 목록은 `zip()`으로 조용히 잘라내지 않는다. 먼저 길이를 검증하거나 `zip(..., strict=True)`를 사용해 불일치를 즉시 드러낸다.
- 한 위치에서 발견된 문제는 대칭적인 구현까지 함께 점검한다. 예를 들어 DOCX에서 명명·검증 문제를 발견하면 PPTX와 XLSX의 대응 코드도 확인한다.

### 예시, 프롬프트, 주석 작성

- 설명용 예시는 특정 업무 사례에 종속시키지 않는다. 과제나 본부 같은 사례 대신 반복 항목, 반복 단위처럼 범용 용어를 사용한다.
- 같은 프롬프트 규칙을 여러 위치에 중복 작성하지 않는다. 공통 문법은 한 곳에서 관리하고 단계별 프롬프트는 각 단계의 허용 범위만 정의한다.
- 주석은 코드의 동작보다 존재 이유와 제약을 설명한다. 임시 작업명, 작성 과정 또는 작업 흔적은 제거한다. 예를 들어 `ponytail`을 사용했다는 사실보다 같은 작업 흔적을 남기지 않아야 하는 이유를 기록한다.

### DTO·dataclass와 클래스 주석

- DTO나 dataclass의 각 필드 앞에는 필드별 역할을 짧은 주석으로 작성한다.
- 필드 주석은 자료형이나 내부 구현이 아니라 실제 처리 과정에서 어디에 사용되는지 쉬운 말로 설명한다. 가능하면 `~할 대상`, `~에 사용할 값`, `~을 식별하는 값`, `~할 때 참고할 정보` 형태로 작성한다.
- 필드 주석에서는 소유권, 상대 좌표의 기준처럼 추상적인 표현을 피하고, 실제 동작과 사용처를 직접 설명한다.
- 클래스 주석은 구현 방식이 아니라 클래스가 맡은 역할을 명사형으로 작성한다. 예를 들어 `반복 항목 삽입 위치 계산기`처럼 표현한다.

### 긴 import 구성

- JavaScript·TypeScript에서 import 구문이 지나치게 길어지면 관련 함수를 하나의 객체로 export하고 그 객체를 import한다.
- 객체의 메서드는 `객체.메서드` 형태로 호출해 관련 동작의 소속과 이름을 함께 드러낸다.
- 예를 들어 여러 함수를 개별 import로 나열하기보다 `rowOperations.transformRelativeTargetToAbsolute()`처럼 사용한다. 단순히 import 줄을 줄이기 위해 서로 무관한 함수를 하나의 객체에 묶지는 않는다.

## 테스트

- 통과하는 테스트가 실제 행위를 검증한다고 가정하지 않는다.
- 사소한 사실만 단언하거나 결과를 확인하지 않는 테스트를 작성하지 않고, 검증해야 할 핵심 행위를 mock으로 치우지 않는다.
- 테스트 이름은 검증하는 행위를 드러내고 결과를 직접 단언한다.
- 금액 계산, 상태 전이 같은 핵심 비즈니스 규칙과 잘못된 입력, 빈 값, 지연, 오류 같은 경계·예외 경로를 상세히 테스트한다.
- 단순 getter, setter, 설정 바인딩이나 프레임워크 내부 동작에는 과도한 테스트를 추가하지 않는다.
- 메서드 호출 횟수 같은 구현 세부보다 사용자 또는 도메인 행위를 검증한다.
- 리팩터링 후에는 관련 테스트뿐 아니라 전체 테스트를 실행한다. 이름 변경은 숨은 호출부 누락을, DTO 검증 강화는 예외 발생 단계 변경을 일으킬 수 있다.

## 전달과 PR

- PR은 작고 리뷰 가능한 범위로 유지하고 의미 있는 커밋으로 나눈다.
- 문제 맥락, 변경 우선순위, 리뷰 지점, 실제 검증 명령과 결과를 제공한다.
- 시각적 변경에는 결과를 확인할 수 있는 스크린샷을 제공한다.
- 장황한 설명이나 자체 비유 대신 정확한 도메인 용어를 사용한다.
- 리뷰어가 알아야 할 도메인 용어가 저장소에 정의되지 않았다면 `CONTEXT.md`에 정리한다.
